# AI開発チーム基盤 設計メモ (v0.1)

## 1. 目的とスコープ

複数のAIエージェント(役割別)に自律的に開発を進めさせ、その状況の閲覧と指示出しをローカルのWeb GUIから行うための仕組みを作る。

- 対象: Webアプリ、モバイルアプリ(iOS中心、Flutterも想定)
- 実行環境: Mac(ローカル)。Claude Codeが使えることが前提
- 個人PCと会社PCの両方で使う。リポジトリをGitHubに置き、各PCでcloneして0から環境を作る
- 非スコープ(当面): ワークスペース分離、Webhook受信、チケットの自動同期、複数ユーザー対応

## 2. 基本方針

1. エージェントの実行基盤は自作せず、Claude Codeのヘッドレス実行/Agent SDKをワーカーとして使う
2. オーケストレーター(進行管理)はLLMではなく普通のコードで書く
3. 作る役と検証する役は別エージェント、別コンテキストにする
4. 役割間の受け渡しは会話ではなく成果物(ファイル)で行う
5. 判定は列挙値で返させ、状態遷移のコードはそれだけを見て動く
6. 状態の正本はローカルSQLite。外部サービス(Notion等)はチケットの入口として軽く使う
7. 安全側に倒す: remoteへのpushは一切させない(第7章)
8. 最初は固定パイプライン。自由な自律判断は慣れてから広げる

## 3. 全体構成

- ローカルサーバー(Node/TypeScript想定): タスクキュー、状態遷移、エージェント起動、イベント配信
- SQLite: タスク、実行履歴、イベントログ、成果物の索引
- GUI(React/Vite想定): 実行状況の閲覧、チケット投入、承認、停止、再実行。リアルタイム配信はSSE
- 役割定義: `roles/*.md`(1ファイル1役割。プロンプト、使える道具、成果物形式)
- プロジェクト登録: 対象リポジトリのパスと、プロジェクトプロファイル
- 作業環境: タスクごとにgit worktreeを作成し、その中だけで作業させる

## 4. 役割

| 役割 | 入力 | 成果物 | 判定 | 権限 |
|---|---|---|---|---|
| プランナー | チケット本文、プロジェクトプロファイル | `plan.md`(要件、受け入れ条件、起動する役割) | ready / need_human | 読み取りのみ |
| 設計者 | plan、既存コード | `design.md` | ready / need_human | 読み取り+docs書き込み |
| デザイナー | plan、既存UI | `ui-spec.md`(設計時)、`design-review.md`(実装後) | ready / approve / changes_requested | docs・デザイン成果物のみ |
| 実装者 | plan、design、ui-spec | コミット、テスト、`impl-notes.md` | done / blocked / need_human | worktree内のみ書き込み可 |
| レビュワー | diff、plan、design | `review.md` | approve / changes_requested / need_human | 読み取りのみ |
| QA | 受け入れ条件、動くアプリ | `qa-report.md`+証拠(スクショ、動画、ログ)、保存したフロー | passed / failed / need_human | 実行可、コード変更不可 |
| 統合担当 | 承認済みの変更 | ローカルブランチ、PR本文の下書き、変更履歴 | done / blocked | ローカルgit操作のみ(pushしない) |

後から追加する候補: プロジェクト把握担当(オンボーディング)、デバッガー、テスト設計者、セキュリティレビュワー。

### 役割の起動ルール

- タスクの大きさで起動する役割を変える(小さなバグ修正は 実装者→レビュワー→QA だけ、など)
- UIに関係しないタスクではデザイナーを呼ばない
- 全役割に「人間に聞く」出口(need_human)を持たせる。推測で進めない

### 最小構成(フェーズ1)

プランナー、実装者、レビュワー、QAの4役。設計者とデザイナーは一周動いてから追加する。

## 5. タスクの状態遷移

```
queued
  → planning(プランナー)
  → [人間承認: 計画]
  → designing(設計者/デザイナー。不要なら飛ばす)
  → [人間承認: デザイン仕様]  ※UIを伴うタスクのみ
  → implementing(実装者)
  → reviewing(レビュワー)
       ├ changes_requested → implementing
       └ approve → qa
  → qa(QA)
       ├ failed → implementing(必要ならデバッガー経由)
       └ passed → [人間承認: 最終確認(見た目・挙動)]
  → integrating(統合担当: ローカルブランチ+PR本文下書き)
  → done
```

- どの状態からでも `needs_input`(人間の回答待ち)、`failed`、`cancelled` に移れる
- 差し戻し(レビュー/QAの往復)は3回まで。超えたら自動で `needs_input`
- 承認ポイントは「計画」「最終確認」の2か所を基本とし、デザインにこだわるタスクでは「デザイン仕様」も加える。慣れたら省略可能にする
- `needs_input` はGUIで目立たせる(放置されやすいため)

## 6. 成果物と判定の受け渡し

- タスクごとにディレクトリを持ち、各役割の成果物を保存する(ローカルのデータディレクトリ配下)
- 各成果物の先頭に、機械が読める形式(JSON等)で判定を残す。状態遷移はこれだけを見る
- 会話ログと成果物は全部残し、「なぜその判断をしたか」を後から追えるようにする

## 7. 安全方針(個人・会社共通)

会社のコードを触らせる前提で、個人利用でも同じ安全側の設定にする。

### 7.1 pushをさせない

- エージェントはローカルのworktreeとローカルブランチまで。remoteへのpush、PR作成、リモートブランチ操作は行わない
- 多層で防ぐ:
  1. Claude Codeの権限設定で `git push`、`gh pr create` などをdeny
  2. worktree/リポジトリに `pre-push` フックを入れ、実行されたら必ず失敗させる
  3. エージェント実行時の環境にGitHubの認証情報(トークン、SSH鍵)を渡さない
- pushとPR作成は人間が手元で行う。統合担当は、ブランチ名、変更履歴、PR本文の下書きを成果物として用意するところまで

### 7.2 そのほか

- 書き込み範囲はworktree内に限定。worktree外への書き込みを禁止する
- シークレット類(`.env`、鍵、認証情報ファイル)は読ませない
- 危険なコマンド(再帰的な削除、システム設定変更など)はdeny
- ネットワークは必要最小限(パッケージ取得など)。許可ドメインは設定で管理する
- 上限: タスクごとのトークン/時間、リトライ回数、同時実行数(初期は2〜3)。超えたら `needs_input`
- 会社用の追加制限が必要になったら、プロジェクト単位の設定で強められるようにしておく(ワークスペース概念は導入しない)

### 7.3 利用前の確認事項(会社)

- AIコーディングツールの利用可否、ソースコードを外部APIに送ってよい範囲、使うアカウント(会社契約か個人か)
- 個人で作ったツールを会社で使うことについて、就業規則(副業・知的財産)

## 8. チケット連携(Notion中心、軽く)

### 8.1 入口

- GUIにNotionのページURLを貼ると、タイトルと本文(仕様・不具合内容)を取り込み、ローカルのタスクを作成する。元ページへのリンクを保持
- ローカルのGUIから直接タスクを作る入口も用意する(外部サービスなしで動かせる)
- 自動ポーリングは行わない
- 会社のNotionのチケットは「1ページ=1チケット、本文に仕様や不具合内容」の形式。本文をそのままプランナーへの入力にし、必要な要点は `plan.md` に写して、写した版を実行時の基準にする

### 8.2 取得方法

- Notion APIの専用インテグレーション(対象DBのみ共有、読み取り専用)を第一候補にする
- 会社のNotionでインテグレーションを作れない場合に備え、**本文を貼り付けて取り込む**手段も用意しておく

### 8.3 書き戻し

- 初期は書き戻しをしない。計画の要約、PR用の文面、QAの結果は、GUIにコピーしやすい形で表示し、人間がNotionに貼る
- 将来、書き戻しが必要になったら、GUIで内容を確認してから投稿する形で追加する

### 8.4 アダプター分離

チケット元はアダプターとして分離する(Notion、ローカル入力、将来のGitHub Issues)。プロパティやステータスの対応は、プロジェクトごとの設定ファイルに持たせる。

## 9. QA

- プロジェクトプロファイルに「QAの方法」を持たせ、QAは種類別の道具を差し替える
  - Web: ブラウザ操作(ヘッドレスブラウザ、またはClaude in Chrome)
  - モバイル(iOS): iOSシミュレータをMaestro等で操作
  - Flutter: 上記に加え `flutter test` / integration_test を併用
- 成果物の形式は共通(合否、証拠、再現手順)にして、GUIは種類を意識せず表示できるようにする
- QAは受け入れ条件を1つずつ確認し、通った探索フローはYAML等で保存して次回から決まった手順で再実行する
- Flutterは、操作対象のUI部品にSemanticsラベルを付ける規約をプロジェクトプロファイルと実装者/デザイナーの役割に入れる
- シミュレータは共有資源として貸し出し管理する(1タスク1台、足りなければ待機)
- 実機が必要な確認(カメラ、センサー、プッシュ通知など)は自動QAの対象外とし、人間の確認ポイントに回す
- 見た目の良さは自動判定しきれないため、デザイナーのレビュー+人間の最終承認で担保する

## 10. デザインの進め方

- デザイナーが先に、プロジェクトごとのデザイン方針(トーン、余白、配色、コンポーネントのルール)を文書化し、実装・レビューの基準にする
- QA時のスクショをデザイナーが仕様と見比べてレビューする(`design-review.md`)
- 最終的な見た目の判断は、GUIでの人間承認で行う

## 11. 別PCでの運用(GitHubでの共有)

- このツールのリポジトリをGitHubに置き、別のPCでcloneして0から環境を作る
- リポジトリに入れるもの: サーバー、GUI、役割定義、状態遷移の定義、設定のサンプル、`doctor` コマンド
- リポジトリに入れないもの(`.gitignore`): 実行履歴のDB、ログ、成果物、PC固有の設定(対象プロジェクトのパス、トークン等)。ローカルのデータディレクトリ(例: `~/.agent-team/`)に置く
- ツール本体のリポジトリには、会社固有の情報(社名、プロジェクト名、チケット内容)を入れない
- セットアップは `git clone` → `npm install` → 起動、で動く形にする
- `doctor` コマンドで前提(Claude Code、Node、git、Xcode、Maestro、Flutter等)を検査し、足りないものを教える。使えない機能は無効化して起動できるようにする
- 役割定義はMarkdownなので、調整した内容もGitHub経由でそのまま共有される
- 個人PCと会社PCは別々にcloneして独立して動かす。両PC間でプロジェクトやタスクの履歴は引き継がない

## 12. データモデル(概要)

- `projects`: id、名前、リポジトリのパス、プロファイル(ビルド/テスト/起動方法、QAの方法、規約)
- `tasks`: id、project_id、タイトル、本文、取り込み元(種別、URL)、状態、優先度、作成/更新日時
- `runs`: id、task_id、役割、状態、開始/終了、判定、使用トークン/時間
- `events`: id、run_id、種別、内容、日時(会話・ツール実行ログ、GUIへの配信元)
- `artifacts`: id、task_id、run_id、種別、パス、判定
- `approvals`: id、task_id、種別(計画/デザイン/最終)、結果、コメント、日時

## 13. 開発フェーズ

1. **フェーズ0**: 本設計メモを確定し、リポジトリの `CLAUDE.md` / `docs/` に置く
2. **フェーズ1**: CLIのみで一周させる(チケット→worktree→プランナー→実装者→レビュワー→QA→ローカルブランチとPR本文下書き)。安全設定(7.1)もここで実装
3. **フェーズ2**: 読み取り専用GUI(タスク一覧、実行状況、ログ、成果物の閲覧)
4. **フェーズ3**: 操作できるGUI(チケット投入、承認、停止、再実行、Notion取り込み)
5. **フェーズ4**: 設計者、デザイナーの追加。このツール自身を最初の対象プロジェクトにして、以降の開発をツール自身に行わせる
6. **フェーズ5**: モバイルQA(iOSシミュレータ)、Flutter対応、書き戻し等の拡張

各フェーズは縦に薄く通す(小さくても最初から最後まで動く状態にする)。
