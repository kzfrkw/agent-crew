## 1. 目的とスコープ

複数のAIエージェント(役割別)に自律的に開発を進めさせ、その状況の閲覧と指示出しをローカルのWeb GUIから行うための仕組みを作る。

- 対象: Webアプリ、モバイルアプリ(iOS中心、Flutterも想定)
- 実行環境: Mac(ローカル)。Claude Codeが使えることが前提
- 個人PCと会社PCの両方で使う。リポジトリをGitHubに置き、各PCでcloneして0から環境を作る
- 非スコープ(当面): ワークスペース分離、Webhook受信、チケットの自動同期、複数ユーザー対応

## 2. 基本方針

1. エージェントの実行基盤は自作せず、Claude Codeのヘッドレス実行/Agent SDKをワーカーとして使う
2. 進め方(次にどの役割を、どの順で呼ぶか)は LLM のコーディネーターが決め、守り(安全、テストの合否、人の承認の関門、上限、記録)はオーケストレーターが普通のコードで受け持つ。オーケストレーターはコーディネーターの一手を検証してから実行する(v0.21。フェーズ10で移行する。移行するまでは固定の状態遷移で動く)
3. 作る役と検証する役は別エージェント、別コンテキストにする
4. 役割間の受け渡しは会話ではなく成果物(ファイル)で行う
5. 判定は列挙値で返させる。守りの検証(テストの合否、関門、上限)はコードがそれと実行の記録だけを見て行う。進め方はコーディネーターが判定と成果物を読んで決める(v0.21)
6. 状態の正本はローカルSQLite。外部サービス(Notion等)はチケットの入口として軽く使う
7. 安全側に倒す: remoteへのpushは一切させない(第7章)
8. 最初は固定パイプラインで始めた(フェーズ1〜9)。v0.21 から進め方を LLM に任せ、固定の流れは「既定の進め方」としてコーディネーターに渡す。守りは広げない
9. 「セッションは消耗品、ファイルが真実」。各役割は新しいセッションで起動し、記憶(会話の履歴)に頼らず、成果物と判断ログを読んで動く
10. 各役割の返答は最小限にする。詳細は成果物(ファイル)に書き、次の役割やオーケストレーターに渡すのは「要約+判定」だけにする
11. 役割ごとにモデルを使い分ける(判断が重い役割に高性能モデル、定型的な役割に軽いモデル)。コストと利用枠の節約が目的

## 3. 全体構成

- ローカルサーバー(Node/TypeScript想定): タスクキュー、状態遷移、エージェント起動、イベント配信
- SQLite: タスク、実行履歴、イベントログ、成果物の索引
- GUI(React/Vite想定): 実行状況の閲覧、チケット投入、承認、停止、再実行。リアルタイム配信はSSE
- 役割定義: `roles/*.md`(1ファイル1役割。プロンプト、使える道具、成果物形式)
- プロジェクト登録: 対象リポジトリのパスと、プロジェクトプロファイル
- 作業環境: タスクごとにgit worktreeを作成し、その中だけで作業させる

### 3.1 実行方式と課金・認証

- **ワーカーは Claude Code のヘッドレス実行(`claude -p`)に決定(v0.7)。** `claude -p` と Agent SDK(TypeScript/Python)は同じエンジンで、違いは「コマンドとして呼ぶか、コードから呼ぶか」。必要な機能(構造化出力、ストリーミング、設定の注入、モデル指定、確認待ちの無効化)は CLI でそろうことを確認した。CLIなら手で同じコマンドを再現してデバッグできる。SDKの利点(`canUseTool` での動的な権限判定、割り込み)が必要になったら(フェーズ3想定)、`src/runner/` の中だけを差し替える
  - 判定の受け取り: `--json-schema` で役割ごとの判定スキーマを渡し、結果の `structured_output` を正とする(列挙値はスキーマで強制される)。成果物の先頭にも判定を書かせ、オーケストレーターが両者の一致と成果物の存在を検査する。不一致や欠落は `needs_input`
  - 進捗のGUI配信: `--output-format stream-json`(コストは `total_cost_usd` で取得)
  - 差し戻し時の文脈の引き継ぎ: セッションIDと `--resume`
  - 権限制御: `--tools`(使える道具)、`--settings`(実行ごとに生成する deny/allow とサンドボックス)、`--permission-mode dontAsk`、`--permission-prompts none`
  - モデル: `roles/*.md` の `model`(`opus` / `sonnet` / `haiku` / `fable` のエイリアス、または正式名)を `--model` に、`effort` を `--effort` に渡す。実際に使ったモデルは結果の `modelUsage` から `runs` に記録する
- **課金は、サブスクの範囲内に収める方針。**
  - Pro/Maxのサブスクで動かす限り、追加課金は自動では発生しない。追加課金が発生するのは、(a)「追加利用(extra usage)」を自分でオンにしたとき、(b) 環境変数 `ANTHROPIC_API_KEY` が設定されているとき(APIの従量課金になる)
  - 公式サポートページ(2026-10-07更新)の状況: 6月に告知された「Agent SDK/`claude -p` の利用を、サブスクの利用枠から切り離して別の月次クレジットにする」変更は、一時停止を経て撤回された。代わりに、Max/Teamプランには月次のAPIクレジットが付くようになった(Claude Consoleで受け取り、APIキーで使う)。サブスクのOAuthで `claude -p` を実行したときは、これまで通り利用枠から消費されるとみている(記事に明記はないため、運用しながら確認する)。仕様は変わりやすいので、運用開始前に最新を確認する
  - Maxに付くAPIクレジットを使う案(APIキー方式。`--bare` も使える)は選択肢として残す。ただし採用するなら、`ANTHROPIC_API_KEY` を警告する `doctor` の方針と、認証情報の扱いを見直す必要がある。当面はOAuth+サブスクの利用枠で動かす
  - 利用枠は対話利用(チャット、Claude Codeの対話)と共有される。Proの枠では、複数エージェントの並列実行にはかなり小さい可能性がある。同時実行数は低めから始め、消費ペースを見てプランを判断する
- **`--bare` の制約**: `--bare` は設定・フック・`CLAUDE.md` などの自動読み込みを止める推奨モードだが、サブスクのログインを使えず、`ANTHROPIC_API_KEY`(従量課金)が必須。サブスクで動かす場合は使えない
- **`--bare` なしの `-p` 実行の注意点**: 対象リポジトリの `.claude/settings.json` のフックと `.mcp.json` のサーバーが、信頼確認なしで実行される。会社のリポジトリでは、リポジトリ側の設定が動くことを前提に、実行前に内容を確認できる仕組み(`doctor` やGUIでの警告)を用意する
- 安全設定(第7章)は、`--bare` に頼らず、ツール側から渡す設定とdeny、フックで効かせる。具体的には、`--setting-sources ""`(対象リポジトリの設定とユーザー設定の両方を読まない)、`--strict-mcp-config`(`.mcp.json` を読まない)、`--settings` で `disableAllHooks` と deny/allow とサンドボックスを渡す。実験で、リポジトリ側のフックが実行されないこと、サブスクのOAuthのまま動くことを確認した(詳細は `docs/safety.md`)
- ユーザー設定(`~/.claude/settings.json`)も読ませないのは、対話用の広い許可(ホームディレクトリ全体の読み取りなど)や個人のフックが、エージェントに効いてしまうため
- 対象リポジトリの `CLAUDE.md` は読み込まれる。規約として有用なので許容し、会社のリポジトリでは、プロファイルを承認するときに人が中身を確認する
- 会社で使うアカウント(会社契約のサブスクかAPIか)は、会社のルールに従って決める

## 4. 役割

| 役割 | 入力 | 成果物 | 判定 | 権限 |
|---|---|---|---|---|
| プランナー | チケット本文、プロジェクトプロファイル | `plan.md`(要件、受け入れ条件、起動する役割) | ready / need_human | 読み取りのみ |
| 設計者 | plan、既存コード | `design.md` | ready / need_human | 読み取り+docs書き込み |
| デザイナー | plan、既存UI | `ui-spec.md`(設計時)、`design-review.md`(実装後) | ready / approve / changes_requested | docs・デザイン成果物のみ |
| 実装者 | plan、design、ui-spec | コミット、テスト、`impl-notes.md` | done / blocked / need_human | worktree内のみ書き込み可 |
| レビュワー | diff、plan、design | `review.md`+重大度つきの指摘(`findings`) | approve / changes_requested / need_human | 読み取りのみ |
| QA | 受け入れ条件、動くアプリ | `qa-report.md`+証拠(スクショ、動画、ログ)、保存したフロー | passed / failed / need_human | 実行可、コード変更不可 |
| 統合担当 | 承認済みの変更 | ローカルブランチ、PR本文の下書き、変更履歴 | done / blocked | ローカルgit操作のみ(pushしない) |
| 監査担当(内部の役割。レビュワーの中で動く) | Must 指摘の一覧、diff、`review.md` | `audit.md`+指摘ごとの判定(`judgments`) | upheld / overturned / need_human | 読み取りのみ(成果物ディレクトリにだけ書ける。Bash なし) |
| プロジェクト把握担当(登録時のみ) | リポジトリのパス | プロジェクトプロファイル(ビルド/テスト/起動方法、構成、規約、QAの方法、テスト基盤の有無と種類) | ready / need_human | 読み取り+ビルド/既存テストの実行。書き込みはプロファイルのみ(データディレクトリ側) |

後から追加する候補: デバッガー、テスト設計者(テストだけを書く別役割。後述のテスト方針を参照)、セキュリティレビュワー。

### 役割ごとのモデル(初期の割り当て案)

| 役割 | モデル | 理由 |
|---|---|---|
| プランナー | 高性能(Opus系) | 要件整理と受け入れ条件の質が全体を左右する |
| 設計者 | 高性能(Opus系)。v0.12: 利用枠(Pro)を考えて Sonnet で始める | 設計判断の質が成果に直結する |
| デザイナー | 高性能(Opus系)。v0.12: 利用枠(Pro)を考えて Sonnet で始める | 見た目の判断とデザイン仕様の一貫性が必要 |
| 実装者 | 標準(Sonnet系) | コーディングは標準モデルで十分 |
| レビュワー | 高性能(Opus系) | 見落としの防止に高い判断力が必要 |
| 監査担当 | 標準(Sonnet系) | 指摘ごとにコードを読んで事実確認する定型的な作業。判断の重さは reviewer が持つ |
| QA | 標準(Sonnet系) | 手順に沿った確認が中心 |
| 統合担当 | 標準(Sonnet系) | 定型作業 |
| プロジェクト把握担当 | 高性能(Opus系) | 作るプロファイルが以降の全タスクの前提になる(登録時に1回だけ動く) |

- モデルは役割定義ファイルの `model` で指定する(コード変更なしに調整できる)
- 実際の割り当ては、利用枠の消費と品質を見ながら調整する。まずは標準モデルを基本にし、品質が足りない役割から上げる進め方もあり

### 役割定義ファイル(`roles/*.md`)の形式

- 先頭(frontmatter)に、`name`、`model`、`effort`、`tools`(使える道具)、`permissions.write`(`none` / `artifacts` / `worktree`)、`verdicts`(判定の列挙値)、`outputs`(成果物の形式)、`timeoutSec`、`maxBudgetUsd`、`resume`(差し戻し時に前回のセッションを再開するか。既定はオフで、新しいセッションで成果物を読ませる)を書く
- `permissions.write` は、ランナーで「`--tools`」「パスを絶対パスで指定した Edit/Write の allow」「サンドボックスの書き込み範囲」の3つに変換して強制する(`docs/safety.md` 3.2)。読み取り専用の役割も、成果物ディレクトリにだけは書ける
- 本文に、役割のプロンプト(責務、判断基準、やってはいけないこと、返答のルール)を書く
- 返答のルール: 「結果の要約と判定だけを返す。コードの全文や長いログは返さず、成果物に書く」を全役割に共通で入れる

### テスト方針

- **基本はテスト先行(テスト駆動)。** 実装者は、受け入れ条件に対応する自動テストを先に書き、失敗することを確認(Red)してから、実装して通し(Green)、整理する(Refactor)。失敗確認と最終の全テスト結果を `impl-notes.md` に残す
  - 理由: テストが仕様を実行できる形にし、レビュワー・QAの検証を助ける。AIが実装を進める中での退行を検知できる。長期的に回帰を防ぐ資産になる
- **テスト先行の例外**(プランナーが `plan.md` に明記し、計画承認の場で人間が確認する): UIの見た目・レイアウト中心の変更、設定やドキュメントのみの変更、探索的な試作。例外でも、後追いでテストを書くか、QAの確認項目として明示する
- **バグ修正**は、再現するテストを先に書いて失敗を確認してから直す(例外なし)
- **受け入れ条件との対応**を `impl-notes.md` に書く(各条件をどのテストで確認しているか。テストで確認できない条件は、QAの確認対象として明示する)
- **自己採点の防止**(同じエージェントがテストと実装の両方を書くと甘くなりうるため):
  - 実装者は、最初に書いたテストを、通すために弱める・削除する・スキップすることを禁止する。変更が必要なら理由を `impl-notes.md` に書く
  - レビュワーは、テストファイルの差分を重点的に確認する(受け入れ条件を実際に検証しているか、アサーションが薄くないか、不自然な変更がないか)
  - 運用してみて甘さが目立つ場合は、テスト設計者(テストだけを書く別役割)を追加し、実装者は、そのテストを通す役に分ける
- **QAとの分担**: 実装者のテストは「コードが仕様どおり動く」ことの確認。QAは「動くアプリを実際に操作して、受け入れ条件を満たす」ことの確認(UI/E2E)
- **完了条件**: 既存テストと新規テストが全て通っていること。結果を成果物に記録する
- **テスト結果の確認(v0.7)**: 実装者の「テストが通った」という申告は信用せず、実装の直後にオーケストレーターがテストを再実行する。テストはエージェントが書いたコードなので、サンドボックスの外では実行しない。サンドボックス内で、テストコマンドを1回だけ実行する内部の役割 **verifier**(haiku)を起動し、合否は verifier の申告ではなく、stream に残る Bash の終了状態(`is_error`)でツール側が判定する。失敗したら差し戻し(回数に数える)

### レビューの重大度と監査(v0.9)

レビューの指摘の重さを、LLM の言い回しではなく列挙値で持たせ、状態遷移が見られる形にする。誤検知による無駄な差し戻し(実装者のコストと利用枠の消費)を減らすのが狙い。

- **重大度**: レビュワーは指摘ごとに `must` / `should` / `nit` を付けて返す(構造化出力の `findings`。基準は `roles/reviewer.md`)。must は「直さないと承認できない」ものだけ(受け入れ条件の未達、テストの弱体化、失敗する筋書きが書けるバグ、セキュリティ、意図しない挙動の破壊)
- **判定との一致**: Must が1件でもあれば `changes_requested`、無ければ `approve`(Should / Nit だけなら approve にして指摘として残す)。食い違い(Must があるのに approve、Must が無いのに changes_requested)は、推測で進めず `needs_input` にする。検査はコード(`src/orchestrator/review-findings.ts`)で行う
- **監査(auditor)**: `changes_requested` のとき、差し戻す前に、別のエージェント・別のコンテキストが Must 指摘だけを1件ずつ、実際のコードを読んで確かめる(`valid` / `invalid` / `unverifiable`)。結果は `audit.md` と `judgments` に残る
  - **却下の条件を厳しくする**: 却下できるのは、auditor が `overturned` を返し、かつ判定がすべての Must を `invalid`(事実と食い違うコードの箇所を根拠に示す)としているときだけ。判定が足りない、`unverifiable`、判定が無い、は残す。却下されたら approve として QA へ進む(承認は HEAD に紐づく)
  - 差し戻した場合、実装者は `audit.md` で `invalid` とされたレビューの指摘を対応不要として扱う。前の周回の `audit.md` は、次のレビューの前に消す
  - 監査が失敗しても止めない(レビュワーの判定のまま差し戻し、警告のイベントを残す)。`need_human` は人に確認する
  - 状態遷移は変えない。verifier と同じく、監査担当は reviewing の中で動く内部の役割で、起動するのは Must があるときだけ(1回余分に動く)。利用枠が厳しいときは `config.json` の `review.audit: false` で止められる
- **GUI**: 指摘の件数(`review_findings`)と監査の結果(`audit`)をアクティビティに出す
- 実運用で、却下される Must がほとんど無ければ監査は不要、多ければ reviewer の基準(`roles/reviewer.md`)を見直す。判断の材料は `runs` と `events` に残る

### 役割の起動ルール

- タスクの大きさで起動する役割を変える(小さなバグ修正は 実装者→レビュワー→QA だけ、など)
- UIに関係しないタスクではデザイナーを呼ばない
- 全役割に「人間に聞く」出口(need_human)を持たせる。推測で進めない

### 最小構成(フェーズ1)

プランナー、実装者、レビュワー、QAの4役に、登録時のみ動くプロジェクト把握担当を加えた構成。設計者とデザイナーは一周動いてから追加する。

## 5. タスクの状態遷移

v0.21 から、この図は「既定の進め方」としてコーディネーターに渡す(14章)。コーディネーターは理由を書いて外れてよいが、人の承認(計画・最終確認)と、テストの再実行の合格を飛ばして完了にはできない。フェーズ10で移行するまでは、この図のとおり固定で動く。

```
queued
  → planning(プランナー)
  → [人間承認: 計画]
  → designing(設計者/デザイナー。不要なら飛ばす。複数リポジトリのタスクでは設計者は必須)
  → [人間承認: デザイン仕様]  ※UIを伴うタスクのみ
  → implementing(実装者)
  → reviewing(レビュワー)
       ├ changes_requested → implementing
       └ approve → qa
  → qa(QA)
       ├ failed → implementing(必要ならデバッガー経由)
       └ passed → [人間承認: 最終確認(見た目・挙動)]
  → integrating(統合担当: ローカルブランチ+PR本文下書き)
  → done
```

- どの状態からでも `needs_input`(人間の回答待ち)、`human_working`(人が手作業中。5.2参照)、`failed`、`cancelled` に移れる
- 差し戻し(レビュー/QAの往復)は3回まで。超えたら自動で `needs_input`
- 承認ポイントは「計画」「最終確認」の2か所を基本とし、デザインにこだわるタスクでは「デザイン仕様」も加える。慣れたら省略可能にする
- `needs_input` はGUIで目立たせる(放置されやすいため)

### 5.1 プロジェクト登録フロー(最初に1回)

1. GUI/CLIで対象リポジトリのパスを登録する
2. プロジェクト把握担当が調査する(読み取りが中心。ビルドと既存テストの実行を試す)。ビルド/テスト/起動方法、構成、規約、QAの方法、テスト基盤の有無と種類を、プロジェクトプロファイルにまとめる
3. 人間がプロファイルを確認・修正して承認する
4. **テスト基盤が無い、または不十分なら、「テスト基盤整備」タスクを自動で作成する。** 通常のパイプライン(計画 → [計画承認] → 実装 → レビュー → QA)で進める。対象プロジェクトのコードを変更するため、計画承認は必須。整備が完了するまで、そのプロジェクトの通常タスクは開始しない(テスト先行の例外として人間が承認した場合を除く)
5. Flutter/iOSなど、プラットフォームごとのテスト基盤(`flutter test`、XCTestなど)も、プロファイルの「QAの方法」と合わせて記録する

### 5.2 人による手作業との並行(ハンドオフ)

同じソースコードに対して、エージェントと人が**交互に**作業する(同時には触らない)ことを前提にする。AIが途中まで進めたものに、人が手を加えるケースも含む。

- **作業場所**: 人も、**そのタスクのworktreeを開いて**編集する。GUI/CLIに「エディタで開く」を用意する。普段のフォルダには触れない。gitは同じブランチを複数のworktreeで同時にチェックアウトできないため、人が別の場所でタスクのブランチを開く方式は避ける
- **`human_working` 状態**: 「人が引き取る」操作で、そのタスクのエージェントの実行を止めてロックする。ロック中はエージェントを起動しない。「エージェントに戻す」操作でロックを解除する
- **戻すときの処理**: 未コミットの変更があれば、「エージェントに戻す」操作を**拒否**し、人に自分でコミットしてもらう(v0.7で決定)。エージェントのコミットには trailer(`Agent-Crew-Role: implementer` など)を付け、trailer の無いコミットを人の変更として記録する。人の変更の差分の要約を、次の役割への入力に加える
- **承認の失効**: 人が変更した後は、それまでのレビューとQAの結果を失効させ、**レビューからやり直す**(小さな修正でも省略しない)。承認は「承認した時点のコミット」に紐づけ、新しいコミットがあれば無効とする
- **成果物の更新**: 人が方針を変えた場合は、`plan.md` や `design.md` を人が直すか、プランナー/設計者に再評価させる。ツールがそのことを促す
- **ベース更新**: 本体のコードが進んでいるとき、タスクのブランチを最新に追従させる操作を用意する。衝突したら `needs_input` にして、人が解決する。統合の前に毎回チェックする
  - v0.7で決定: 取り込みは merge(エージェントのコミットの SHA を変えないため)。マージコミットには trailer `Agent-Crew-Role: base-update` を付け、人の変更と区別する。レビュー以降の段階で取り込んだら、承認を失効させてレビューからやり直す。衝突したらマージを中止して `needs_input` にし、人が引き取って解決する(`task takeover` → 解決してコミット → `task return`)
  - 自動化の範囲(フェーズ1): 統合担当の直前に「ベースに追従しているか」を確認し、進んでいれば人に `task update-base` を促す。自動では取り込まない
- **実行中の警告**: エージェントが動いているworktreeには、「実行中のため触らないでください」と表示する
- **worktreeの準備**: 依存パッケージやビルド結果はworktreeごとに必要になる。準備手順はプロジェクトプロファイルに記載する

### 5.3 複数リポジトリにまたがるタスク

会社のメインサービスのように、フロントエンドとバックエンドなどが別リポジトリのケースを想定する。

- **プロジェクトは「1つ以上のリポジトリのまとまり」**とし、各リポジトリに役目(フロント、バックエンドなど)を持たせる。プロファイルは2段にする
  - リポジトリごと: ビルド、テスト、規約
  - プロジェクト全体: 全体の起動方法(両方を立ち上げる手順)、API仕様の置き場所、QAの方法
  - プロジェクト把握担当は、リポジトリごとに調べ、プロジェクト全体のプロファイルにまとめる
- **タスクが複数のworktreeを持つ。** プランナーが `plan.md` に「このタスクで変更するリポジトリ」を書き、その分だけworktreeとブランチを作る(ブランチ名は共通にする)
- **インターフェース契約。** 複数リポジトリのタスクでは設計者を必須とし、`design.md` に契約(APIのリクエスト/レスポンスの形など)を書く。これを、各リポジトリの実装者の共通の入力にする
- **実装者はリポジトリごとに別々に、順番に動かす**(バックエンド→フロントが基本)。各実装者は、自分のリポジトリのworktreeにだけ書き込める。権限が絞れて安全で、セッションの文脈も小さく済む
- **レビュー**: リポジトリごとの差分に加え、「契約と合っているか」を横断で確認する
- **QA**: プロジェクトプロファイルの「全体の起動方法」で、関係するリポジトリを一緒に立ち上げて確認する
- **統合**: リポジトリごとにローカルブランチとPR本文の下書きを作る。マージの順序と、PR同士の相互リンクをまとめて提示する。pushとPR作成は、これまで通り人が行う
- **サンドボックスの書き込み許可**は、そのタスクのworktree(複数)だけにする。**ハンドオフ**(5.2)は、そのタスクの全worktreeをまとめてロックする
- 当面は、全リポジトリを書き込み可として扱う。「参照のみ」の区分は、必要になった時点で追加する
- **フェーズ1は1リポジトリで進める**が、データの形(`projects`、`repos`、`task_repos`)は、最初から複数リポジトリを許す形にする

## 6. 成果物と判定の受け渡し

- タスクごとにディレクトリを持ち、各役割の成果物を保存する(ローカルのデータディレクトリ配下)
- 各成果物の先頭に、機械が読める形式(JSON等)で判定を残す。状態遷移はこれだけを見る
- 会話ログと成果物は全部残し、「なぜその判断をしたか」を後から追えるようにする
- **設計判断ログ(`decisions.md`)をプロジェクトごとに持つ。** 設計者・デザイナーが、重要な設計判断とその理由を追記し、次のタスクの各役割が読む。タスクごとの `design.md` が、このプロジェクトの判断の蓄積と矛盾しないようにするため。会社のリポジトリにファイルを増やさないよう、置き場所はツールのデータディレクトリ側(例: `~/.agent-team/projects/<id>/decisions.md`)とし、必要に応じてworktreeに読み取り用にコピーする
- 役割間やオーケストレーターに渡す内容は「要約+判定」だけ。詳細は成果物のパスで参照する(記憶のあふれと、コストの増加を防ぐ)

## 7. 安全方針(個人・会社共通)

会社のコードを触らせる前提で、個人利用でも同じ安全側の設定にする。

### 7.1 pushをさせない

- エージェントはローカルのworktreeとローカルブランチまで。remoteへのpush、PR作成、リモートブランチ操作は行わない
- 多層で防ぐ:
  1. Claude Codeの権限設定で `git push`、`gh pr create` などをdeny
  2. `pre-push` フックで、実行されたら必ず失敗させる。対象リポジトリの `.git/hooks` に置くと人の push まで止まるため、worktreeごとの設定(`extensions.worktreeConfig` と `git config --worktree core.hooksPath`)で、**エージェントのworktreeにだけ**効かせる。それ以外のフックは元のフックに中継する。このツール自身のリポジトリでは、`CLAUDECODE` / `AGENT_CREW_RUN` の環境変数があるときだけ失敗するフックを `githooks/` に置く
  3. エージェント実行時の環境にGitHubの認証情報(トークン、SSH鍵)を渡さない。環境変数は許可リスト(`PATH`、`HOME`、`LANG` など)だけを渡し、`SSH_AUTH_SOCK`、`GITHUB_TOKEN` などは落とす。`~/.ssh` などはサンドボックスの `credentials` で読み取りを拒否する
- pushとPR作成は人間が手元で行う。統合担当は、ブランチ名、変更履歴、PR本文の下書きを成果物として用意するところまで

### 7.2 そのほか

- 書き込み範囲はworktree内に限定。worktree外への書き込みを禁止する
- シークレット類(`.env`、鍵、認証情報ファイル)は読ませない
- 危険なコマンド(再帰的な削除、システム設定変更など)はdeny
- ネットワークは必要最小限(パッケージ取得など)。許可ドメインは設定で管理する
- 上限: タスクごとのトークン/時間、リトライ回数、同時実行数(初期は1〜2)。超えたら `needs_input`。利用枠の消費ペースを見ながら、同時実行数を調整する(3.1参照)
- 会社用の追加制限が必要になったら、プロジェクト単位の設定で強められるようにしておく(ワークスペース概念は導入しない)

### 7.3 サンドボックス

Claude Codeのサンドボックス(Bashコマンドを、OSの機能で囲いの中に閉じ込める仕組み)を採用し、7.1・7.2の仕組み(許可設定、`pre-push` フック、認証情報を渡さない)と**重ねて**使う。

- 設定の方向性(具体値はClaude Codeが最新ドキュメントを見て決める):
  - `sandbox.enabled: true`、`failIfUnavailable: true`(サンドボックスが使えなければ起動しない)
  - `allowUnsandboxedCommands: false`(囲いの外での再試行を禁止)。`--settings` で渡すと「管理者必須」扱いになり、**リポジトリ側の設定ファイルによる囲いの緩和が無視される**ため、会社のリポジトリ対策になる
  - 書き込みは作業ディレクトリ(worktree)を中心にする
  - `sandbox.credentials` で `~/.ssh`、`~/.aws` などの読み取りと、`GITHUB_TOKEN` 等の環境変数を禁止する
  - ネットワークは許可ドメインを最小にする。GitHubへの通信を許可しなければ、サンドボックス内からpushできない
- `.git` 内の `hooks` と `config` は、サンドボックス内から書き換えられない。`pre-push` フックの設置は、ツール側(サンドボックスの外)で行う
- **サンドボックスの外で動くもの**(Read/Edit/Writeツール、WebFetch、MCPサーバー、フック)は、許可設定で制御する(例: worktree外へのEditをdenyする)
- 制約: ネイティブWindowsでは使えない(Macが前提)。docker、一部のGo製CLI、SSH経由のgitなど、失敗するものがある
- **`claude -p` での実験結果(2026-10-08、v0.7)**: 想定どおりに効いた。worktree内の書き込みとコミットはでき、worktree外への書き込み、`~/.ssh` の読み取り、`GITHUB_TOKEN`、github.com への通信、`.git/hooks` への書き込みは拒否された。注意点は2つ。(a) Edit/Write をパス無しで allow にすると、worktree外にも書けてしまう(絶対パスで許可する)。(b) Claude の一時ディレクトリの下に置いたworktreeでは、内側への書き込みも拒否された(worktreeは `~/.agent-team/worktrees/` に置く)。詳細は `docs/safety.md`
- **モバイルQAで必要になる許可(実験結果。フェーズ6で対応)**: `xcodebuild -version` は動く。`xcrun simctl` は CoreSimulatorService に接続できない(`network.allowMachLookup`、だめなら `excludedCommands`)。Flutter は SDK のキャッシュ、`~/.pub-cache` への書き込みと、pub.dev などへの通信が必要。DerivedData と CoreSimulator のディレクトリへの書き込みも必要

### 7.4 利用前の確認事項(会社)

- AIコーディングツールの利用可否、ソースコードを外部APIに送ってよい範囲、使うアカウント(会社契約か個人か)
- 個人で作ったツールを会社で使うことについて、就業規則(副業・知的財産)

## 8. チケット連携(Notion中心、軽く)

### 8.1 入口

- GUIにNotionのページURLを貼ると、タイトルと本文(仕様・不具合内容)を取り込み、ローカルのタスクを作成する。元ページへのリンクを保持
- ローカルのGUIから直接タスクを作る入口も用意する(外部サービスなしで動かせる)
- 自動ポーリングは行わない
- 会社のNotionのチケットは「1ページ=1チケット、本文に仕様や不具合内容」の形式。本文をそのままプランナーへの入力にし、必要な要点は `plan.md` に写して、写した版を実行時の基準にする

### 8.2 取得方法

- Notion APIの専用インテグレーション(対象DBのみ共有、読み取り専用)を第一候補にする
- 会社のNotionでインテグレーションを作れない場合に備え、**本文を貼り付けて取り込む**手段も用意しておく

### 8.3 書き戻し

- 初期は書き戻しをしない。計画の要約、PR用の文面、QAの結果は、GUIにコピーしやすい形で表示し、人間がNotionに貼る
- 将来、書き戻しが必要になったら、GUIで内容を確認してから投稿する形で追加する

### 8.4 アダプター分離

チケット元はアダプターとして分離する(Notion、ローカル入力、将来のGitHub Issues)。プロパティやステータスの対応は、プロジェクトごとの設定ファイルに持たせる。

## 9. QA

- プロジェクトプロファイルに「QAの方法」を持たせ、QAは種類別の道具を差し替える
  - Web: ブラウザ操作(ヘッドレスブラウザ、またはClaude in Chrome)
  - モバイル(iOS): iOSシミュレータをMaestro等で操作
  - Flutter: 上記に加え `flutter test` / integration_test を併用
- 成果物の形式は共通(合否、証拠、再現手順)にして、GUIは種類を意識せず表示できるようにする
- **フェーズ1のQAは、コマンドとHTTPの確認まで**(v0.7で決定): プロファイルのテスト・ビルド・起動コマンドを実行し、受け入れ条件ごとに curl で確認する(サーバーは127.0.0.1で起動し、確認後に止める)。ブラウザ操作はフェーズ2以降
- QAは受け入れ条件を1つずつ確認し、通った探索フローはYAML等で保存して次回から決まった手順で再実行する
- Flutterは、操作対象のUI部品にSemanticsラベルを付ける規約をプロジェクトプロファイルと実装者/デザイナーの役割に入れる
- シミュレータは共有資源として貸し出し管理する(1タスク1台、足りなければ待機)
- 実機が必要な確認(カメラ、センサー、プッシュ通知など)は自動QAの対象外とし、人間の確認ポイントに回す
- 見た目の良さは自動判定しきれないため、デザイナーのレビュー+人間の最終承認で担保する

## 10. デザインの進め方

- デザイナーが先に、プロジェクトごとのデザイン方針(トーン、余白、配色、コンポーネントのルール)を文書化し、実装・レビューの基準にする
- QA時のスクショをデザイナーが仕様と見比べてレビューする(`design-review.md`)
- 最終的な見た目の判断は、GUIでの人間承認で行う

## 11. 別PCでの運用(GitHubでの共有)

- このツールのリポジトリをGitHubに置き、別のPCでcloneして0から環境を作る
- リポジトリに入れるもの: サーバー、GUI、役割定義、状態遷移の定義、設定のサンプル、`doctor` コマンド
- リポジトリに入れないもの(`.gitignore`): 実行履歴のDB、ログ、成果物、PC固有の設定(対象プロジェクトのパス、トークン等)。ローカルのデータディレクトリ(例: `~/.agent-team/`)に置く
- ツール本体のリポジトリには、会社固有の情報(社名、プロジェクト名、チケット内容)を入れない
- セットアップは `git clone` → `npm install` → 起動、で動く形にする
- `doctor` コマンドで前提(Claude Code、Node、git、Xcode、Maestro、Flutter等)を検査し、足りないものを教える。使えない機能は無効化して起動できるようにする
- `doctor` は、環境変数 `ANTHROPIC_API_KEY` が設定されていたら警告する(意図しない従量課金の防止)。あわせて、現在の認証方式(サブスクかAPIか)を表示する
- 役割定義はMarkdownなので、調整した内容もGitHub経由でそのまま共有される
- 個人PCと会社PCは別々にcloneして独立して動かす。両PC間でプロジェクトやタスクの履歴は引き継がない

## 12. データモデル(概要)

- `projects`: id、名前、プロジェクト全体のプロファイル(全体の起動方法、QAの方法、API仕様の置き場所、規約)
- `repos`: id、project_id、パス、役目(フロント/バックエンド等)、リポジトリ単位のプロファイル(ビルド/テスト/規約)
- `task_repos`: task_id、repo_id、worktreeのパス、ブランチ名
- `tasks`: id、project_id、タイトル、本文、取り込み元(種別、URL)、状態、優先度、現在の作業者(エージェント/人)、作成/更新日時
- `runs`: id、task_id、役割、モデル、状態、開始/終了、判定、使用トークン/時間/コスト見積もり
- `events`: id、run_id、種別、内容、日時(会話・ツール実行ログ、GUIへの配信元)
- `artifacts`: id、task_id、run_id、種別、パス、判定
- `approvals`: id、task_id、種別(計画/デザイン/最終)、結果、コメント、日時

### v0.22で決めたこと(フェーズ10に追加: 測れる判定、タスクをまたぐ振り返り。2026-10-17)
- **背景**: エージェントのチームの事例(Agent Teams を PM の感覚で設計する、Managed Agents の Outcomes / Dreaming、サブエージェントの5役構成)と照らすと、役割の境界・作る役と検証する役の分離・書き込み範囲の強制・追跡はすでに満たしている。弱いのは、(a) 判定の基準が定性的(批評のチェックリストの作り込みは 9b に先送り)、(b) 学びが1タスクの振り返りに閉じている、(c) フェーズ10で方式をどう比べるかが決まっていない、の3点。Managed Agents は API 経由の機能と見られ、サブスクの範囲で動かす方針(3.1)と合わない可能性が高いので、乗り換えずに考え方だけを取り込む
- **1. 測れる判定(ルーブリック)**:
  - 判定する役割(critic、reviewer、qa、design_reviewer)ごと、企画では段ごとに、`rubrics/<名前>.md` を置く。項目は測れる形で書く(例: 「主張ごとに出典の URL と取得日がある」「受け入れ条件はすべて Given/When/Then で、境界値を1つ以上含む」「画面ごとに空の状態とエラーの状態がある」)。項目ごとに重大度(must / should)を付ける
  - 判定役は構造化出力で項目ごとの合否と根拠(成果物のどこか)を返す。must の不合格が1つでもあれば `changes_requested`。オーケストレーターは、項目ごとの結果と判定が一致しているかを検査する(Must の有無と判定の一致を見る v0.9 と同じ考え方)
  - ルーブリックは役割の定義と同じく人が書いて直す。コーディネーターや判定役は書き換えない
  - v0.21 との関係: コーディネーターの `complete`(企画では段を進める一手)は、その段のルーブリックの must がすべて合格していることを守りの条件に加える
  - 9b の「段ごとの批評のチェックリストの作り込み」は、これに置き換える
- **2. タスクをまたぐ振り返り**:
  - 今の振り返り(retrospective)は完了した1タスクだけを見る。差し戻しの理由(`events` の `bounce`)、レビューの指摘、人のコメント、却下の理由はすでに SQLite にあるので、プロジェクト全体で集めて、繰り返す失敗と人の好みを見つける
  - 起動の条件: プロジェクトで完了したタスクが前回から N 件(既定 5)増えたとき、または人が `project retro <n>` で起動したとき。新しい役割は足さず、retrospective に「横断」の入力(集めた理由の一覧と件数)を渡す
  - 提案先は今の `conventions` / `decisions` に、役割への補足(`roles/` は変えず、プロジェクトごとの追記として `~/.agent-team/projects/<id>/role-notes/<役割>.md` に置き、起動時に入力へ足す)を加える。反映は人が採用したものだけ(自動の反映はしない)
  - 採用した提案の効果は、3の数値(同じ理由の差し戻しの件数)で後から確かめる
- **3. 数値の使い方**:
  - タスクの大きさと中身はばらばらなので、全タスクの平均の時間・費用は見ない(増減の理由が分からない)。件数が少ないうちの比率も、ぶれが大きいので判断に使わない
  - **方式の比較(フェーズ10の 10-3)**: 同じ題材で比べる。同梱のサンプルの e2e(`npm run e2e:planning`、開発は `npm run e2e`)を、固定の流れとコーディネーターでそれぞれ2〜3回回し、時間・費用・止まった回数・差し戻しの回数・人の介入の回数・ルーブリックの must の初回の合格を `docs/e2e-log.md` に残して比べる。専用の集計コマンドは作らない
  - **理由の内訳**: 止まった理由(`needs_input` の理由)と差し戻しの理由を、種類ごとの件数で集計する(例: テストの失敗、同じ理由の繰り返し、撮影できない)。大きさに左右されにくく、直す場所(役割のプロンプト、ルーブリック、規約)の手がかりになる。2の横断の振り返りの入力にし、規約を採用する前と後の同じ理由の件数で効果を確かめる
  - **週ごとの費用**: `runs.cost_usd` の週ごとの合計を出す。サブスクの枠で足りるか(Pro か Max か)の判断に使う
  - 集計はスキーマを増やさず、`runs`・`events`・`approvals` から行う。CLI は横断の振り返りと一緒に作る(`project retro <n> --stats` で内訳と週ごとの費用を出す)。所要時間を大きさ別に見るなどの集計は、件数が溜まってから考える

### v0.20で決めたこと(実運用で見つかったこと。2026-10-16)
- **引き渡しで開発のプロジェクトを用意する**: 新サービスの企画は、引き渡しの承認で「既存のプロジェクト」「企画のプロジェクトにリポジトリを登録」「別のプロジェクトを作る」から選ぶ。リポジトリは手元のものか、空のフォルダ(ツールが `git init -b main` と空の最初のコミット)。承認でタスクを作り、プロファイルは裏で作って、人がプロジェクト画面で承認する(`docs/structure.md`)

### v0.19で決めたこと(フェーズ9: 企画の流れ)
- **目的**: Web サービス・モバイルアプリの新サービスや、既存サービスの新機能の企画を、調査から要件の整理まで進め、開発の流れ(フェーズ1〜8)にチケットとして引き渡す。開発と同じ基盤(状態の正本は SQLite、成果物はファイル、作る役と検証する役を分ける、人の承認、GUI・通知・利用枠)を使う
- **置き場所**: 今のツールの中に「企画タスク」(タスクの種類 `planning`)を足す。開発タスクとは別の状態遷移を持つ。GUI・CLI・常駐ワーカーは共通。別のツールにはしない(引き渡しが同じ DB の中で済み、改良を一度で済ませるため)
- **流れ(ギャレットの5階層に合わせる)**: 調査(`research.md`)→ 戦略(`strategy.md`。誰の・何の課題を・どう解くか、ペルソナ、成功の指標)→ 要件(`scope.md`。機能一覧、ユーザーストーリー、スコープ外、優先度)→ 構造・骨格(`structure.md`、`skeleton.md`。画面一覧、画面遷移(Mermaid)、データモデルの案、ワイヤーフレーム)→ 引き渡し(`handoff.md` と、開発のチケットの案)。表層(ビジュアル)は開発の流れのデザイナーに任せる
- **書く役と批評する役**: 各段で書く役(調査担当 researcher、企画担当 strategist、要件担当 product、UX 担当 ux、まとめ担当 handoff)のあとに、批評担当(critic)が別のコンテキストで、段ごとのチェックリスト(抜け漏れ、ペルソナから見て価値があるか、前の段との整合、根拠の有無)で検証し、approve / changes_requested を返す。差し戻しは同じ段の書く役に戻す(上限と、同じ理由の繰り返しの検出は開発と同じ)。人の承認は、戦略(方向性)・要件・引き渡しの3か所。調査と構造・骨格は批評だけで次へ進む(人は承認待ちで中身を見られる)
- **調査と Web**: 調査担当だけ、Claude Code の WebSearch / WebFetch を許す(Bash は許さない。書けるのは成果物ディレクトリだけ)。Web の内容は外部の入力として扱い、出典(URL と取得日)を必ず書かせる。批評担当は出典の無い主張を指摘する。サンドボックスの通信の許可(allowedDomains)は広げない(WebSearch / WebFetch は Claude 側の道具で、権限ルールで許可する)
- **ローカルの資料**: 企画タスクに「読む資料」のフォルダやファイル(絶対パス)と、既存サービスの新機能なら対象のプロジェクト(リポジトリ)を紐づけられる。各役割は読むだけ。資料のフォルダにも読ませないパス(フェーズ7)を使える
- **成果物の形**: 正本は Markdown(成果物ディレクトリ)。スライドが要る段(戦略、要件)は、同じ内容を Marp の Markdown(`*.slides.md`)でも書かせる。**HTML / PDF / .pptx への書き出しは後回し**(2026-10-14: Marp CLI を入れると依存に既知の脆弱性が 12 件(high 9。xmldom、katex、basic-ftp、extract-zip)入り、破壊的でない修正では消えなかったため、人と相談して見送った)。人は手元の Marp(VS Code の拡張など)で開く。書き出すときは、ツールの sandbox-exec の中で動かすか、修正版が出てから入れる

### 4b(自己適用)で見つかったことと直したこと(2026-10-10)
- テストの再実行(verifier)では依存の準備(install)をしない。node_modules がある状態での入れ直しがサンドボックスに拒否され(EPERM)、しかも途中で失敗して `node_modules/.bin` を壊した。準備は worktree に書ける実装者の責任
- テストの再実行の結果のキャッシュ(同じコミットなら再実行しない)は、成功だけを使う。失敗をキャッシュすると、環境を直しても再実行されない
- 差し戻し・回答での再開の後で、実装者が「原因は環境でコードの変更は不要」として新しいコミットなしで done を返した場合は、ブランチに実装のコミットがあれば警告を残してテストの再実行・レビューに進める(最初の実装でコミットが無いのは従来どおり止める)
- このリポジトリのテストは、エージェントの環境変数(`AGENT_CREW_ROLE`)が残るとテストの中のコミットにも trailer が付いて失敗した。テスト用の git の環境から外す
- 設計判断ログの日付はこの PC の日付で書く
- QA は、サーバーの起動・確認・停止を1回の Bash の実行で行う(別の実行からの kill はサンドボックスが拒否する)。サンドボックスで確かめられない条件(画面の見た目など)を人が確認したら、QA はそれを合格に数える
- 結果: agent-crew 自身のタスク #1 を、計画から完了まで常駐ワーカーで通した(`docs/e2e-log.md`)
- サンドボックスの中ではヘッドレス Chrome を動かせない(`docs/safety.md` 7章)。画面の確認(QA の見た目、4c のデザインレビュー)は、サンドボックスの外のツールが管理する仕組みで行う
- 役割の実行のたびに、作業ディレクトリの中で、その実行の開始より後に起動されたプロセスを、ツールが止める(`src/runner/cleanup.ts`。止めたものは `cleanup` のイベントに残す)。QA の役割の工夫(1回の Bash で起動・停止)に加えた安全網。実行の前から動いているもの(人の端末など)には触らない
