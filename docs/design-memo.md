## 1. 目的とスコープ

複数のAIエージェント(役割別)に自律的に開発を進めさせ、その状況の閲覧と指示出しをローカルのWeb GUIから行うための仕組みを作る。

- 対象: Webアプリ、モバイルアプリ(iOS中心、Flutterも想定)
- 実行環境: Mac(ローカル)。Claude Codeが使えることが前提
- 個人PCと会社PCの両方で使う。リポジトリをGitHubに置き、各PCでcloneして0から環境を作る
- 非スコープ(当面): ワークスペース分離、Webhook受信、チケットの自動同期、複数ユーザー対応

## 2. 基本方針

1. エージェントの実行基盤は自作せず、Claude Codeのヘッドレス実行/Agent SDKをワーカーとして使う
2. オーケストレーター(進行管理)はLLMではなく普通のコードで書く
3. 作る役と検証する役は別エージェント、別コンテキストにする
4. 役割間の受け渡しは会話ではなく成果物(ファイル)で行う
5. 判定は列挙値で返させ、状態遷移のコードはそれだけを見て動く
6. 状態の正本はローカルSQLite。外部サービス(Notion等)はチケットの入口として軽く使う
7. 安全側に倒す: remoteへのpushは一切させない(第7章)
8. 最初は固定パイプライン。自由な自律判断は慣れてから広げる
9. 「セッションは消耗品、ファイルが真実」。各役割は新しいセッションで起動し、記憶(会話の履歴)に頼らず、成果物と判断ログを読んで動く
10. 各役割の返答は最小限にする。詳細は成果物(ファイル)に書き、次の役割やオーケストレーターに渡すのは「要約+判定」だけにする
11. 役割ごとにモデルを使い分ける(判断が重い役割に高性能モデル、定型的な役割に軽いモデル)。コストと利用枠の節約が目的

## 3. 全体構成

- ローカルサーバー(Node/TypeScript想定): タスクキュー、状態遷移、エージェント起動、イベント配信
- SQLite: タスク、実行履歴、イベントログ、成果物の索引
- GUI(React/Vite想定): 実行状況の閲覧、チケット投入、承認、停止、再実行。リアルタイム配信はSSE
- 役割定義: `roles/*.md`(1ファイル1役割。プロンプト、使える道具、成果物形式)
- プロジェクト登録: 対象リポジトリのパスと、プロジェクトプロファイル
- 作業環境: タスクごとにgit worktreeを作成し、その中だけで作業させる

### 3.1 実行方式と課金・認証

- **ワーカーは Claude Code のヘッドレス実行(`claude -p`)を第一候補にする。** `claude -p` と Agent SDK(TypeScript/Python)は同じエンジンで、違いは「コマンドとして呼ぶか、コードから呼ぶか」。呼び出し部分は `src/runner/` に閉じ込め、後から Agent SDK に差し替えられるようにする
  - 判定の受け取り: `--output-format json` と `--json-schema`
  - 進捗のGUI配信: `--output-format stream-json`(コストは `total_cost_usd` で取得)
  - 差し戻し時の文脈の引き継ぎ: セッションIDと `--resume`
  - 権限制御: `--allowedTools`、`--permission-mode`(`dontAsk` など)、`--permission-prompts none`
- **課金は、サブスクの範囲内に収める方針。**
  - Pro/Maxのサブスクで動かす限り、追加課金は自動では発生しない。追加課金が発生するのは、(a)「追加利用(extra usage)」を自分でオンにしたとき、(b) 環境変数 `ANTHROPIC_API_KEY` が設定されているとき(APIの従量課金になる)
  - 公式サポートページによると、Agent SDK/`claude -p` の利用を、サブスクの利用枠から切り離して別の月次クレジットにする変更は一時停止中で、現状はこれまで通りサブスクの利用枠から消費される。仕様は変わりやすいので、運用開始前に最新を確認する
  - 利用枠は対話利用(チャット、Claude Codeの対話)と共有される。Proの枠では、複数エージェントの並列実行にはかなり小さい可能性がある。同時実行数は低めから始め、消費ペースを見てプランを判断する
- **`--bare` の制約**: `--bare` は設定・フック・`CLAUDE.md` などの自動読み込みを止める推奨モードだが、サブスクのログインを使えず、`ANTHROPIC_API_KEY`(従量課金)が必須。サブスクで動かす場合は使えない
- **`--bare` なしの `-p` 実行の注意点**: 対象リポジトリの `.claude/settings.json` のフックと `.mcp.json` のサーバーが、信頼確認なしで実行される。会社のリポジトリでは、リポジトリ側の設定が動くことを前提に、実行前に内容を確認できる仕組み(`doctor` やGUIでの警告)を用意する
- 安全設定(第7章)は、`--bare` に頼らず、ツール側から渡す設定とdeny、フックで効かせる前提で設計する
- 会社で使うアカウント(会社契約のサブスクかAPIか)は、会社のルールに従って決める

## 4. 役割

| 役割 | 入力 | 成果物 | 判定 | 権限 |
|---|---|---|---|---|
| プランナー | チケット本文、プロジェクトプロファイル | `plan.md`(要件、受け入れ条件、起動する役割) | ready / need_human | 読み取りのみ |
| 設計者 | plan、既存コード | `design.md` | ready / need_human | 読み取り+docs書き込み |
| デザイナー | plan、既存UI | `ui-spec.md`(設計時)、`design-review.md`(実装後) | ready / approve / changes_requested | docs・デザイン成果物のみ |
| 実装者 | plan、design、ui-spec | コミット、テスト、`impl-notes.md` | done / blocked / need_human | worktree内のみ書き込み可 |
| レビュワー | diff、plan、design | `review.md` | approve / changes_requested / need_human | 読み取りのみ |
| QA | 受け入れ条件、動くアプリ | `qa-report.md`+証拠(スクショ、動画、ログ)、保存したフロー | passed / failed / need_human | 実行可、コード変更不可 |
| 統合担当 | 承認済みの変更 | ローカルブランチ、PR本文の下書き、変更履歴 | done / blocked | ローカルgit操作のみ(pushしない) |
| プロジェクト把握担当(登録時のみ) | リポジトリのパス | プロジェクトプロファイル(ビルド/テスト/起動方法、構成、規約、QAの方法、テスト基盤の有無と種類) | ready / need_human | 読み取り+ビルド/既存テストの実行。書き込みはプロファイルのみ(データディレクトリ側) |

後から追加する候補: デバッガー、テスト設計者(テストだけを書く別役割。後述のテスト方針を参照)、セキュリティレビュワー。

### 役割ごとのモデル(初期の割り当て案)

| 役割 | モデル | 理由 |
|---|---|---|
| プランナー | 高性能(Opus系) | 要件整理と受け入れ条件の質が全体を左右する |
| 設計者 | 高性能(Opus系) | 設計判断の質が成果に直結する |
| デザイナー | 高性能(Opus系) | 見た目の判断とデザイン仕様の一貫性が必要 |
| 実装者 | 標準(Sonnet系) | コーディングは標準モデルで十分 |
| レビュワー | 高性能(Opus系) | 見落としの防止に高い判断力が必要 |
| QA | 標準(Sonnet系) | 手順に沿った確認が中心 |
| 統合担当 | 標準(Sonnet系) | 定型作業 |
| プロジェクト把握担当 | 高性能(Opus系) | 作るプロファイルが以降の全タスクの前提になる(登録時に1回だけ動く) |

- モデルは役割定義ファイルの `model` で指定する(コード変更なしに調整できる)
- 実際の割り当ては、利用枠の消費と品質を見ながら調整する。まずは標準モデルを基本にし、品質が足りない役割から上げる進め方もあり

### 役割定義ファイル(`roles/*.md`)の形式

- 先頭(frontmatter)に、`name`、`model`、`permissions`(使える道具、書き込み範囲)、`outputs`(成果物の形式と判定の列挙値)を書く
- 本文に、役割のプロンプト(責務、判断基準、やってはいけないこと、返答のルール)を書く
- 返答のルール: 「結果の要約と判定だけを返す。コードの全文や長いログは返さず、成果物に書く」を全役割に共通で入れる

### テスト方針

- **基本はテスト先行(テスト駆動)。** 実装者は、受け入れ条件に対応する自動テストを先に書き、失敗することを確認(Red)してから、実装して通し(Green)、整理する(Refactor)。失敗確認と最終の全テスト結果を `impl-notes.md` に残す
  - 理由: テストが仕様を実行できる形にし、レビュワー・QAの検証を助ける。AIが実装を進める中での退行を検知できる。長期的に回帰を防ぐ資産になる
- **テスト先行の例外**(プランナーが `plan.md` に明記し、計画承認の場で人間が確認する): UIの見た目・レイアウト中心の変更、設定やドキュメントのみの変更、探索的な試作。例外でも、後追いでテストを書くか、QAの確認項目として明示する
- **バグ修正**は、再現するテストを先に書いて失敗を確認してから直す(例外なし)
- **受け入れ条件との対応**を `impl-notes.md` に書く(各条件をどのテストで確認しているか。テストで確認できない条件は、QAの確認対象として明示する)
- **自己採点の防止**(同じエージェントがテストと実装の両方を書くと甘くなりうるため):
  - 実装者は、最初に書いたテストを、通すために弱める・削除する・スキップすることを禁止する。変更が必要なら理由を `impl-notes.md` に書く
  - レビュワーは、テストファイルの差分を重点的に確認する(受け入れ条件を実際に検証しているか、アサーションが薄くないか、不自然な変更がないか)
  - 運用してみて甘さが目立つ場合は、テスト設計者(テストだけを書く別役割)を追加し、実装者は、そのテストを通す役に分ける
- **QAとの分担**: 実装者のテストは「コードが仕様どおり動く」ことの確認。QAは「動くアプリを実際に操作して、受け入れ条件を満たす」ことの確認(UI/E2E)
- **完了条件**: 既存テストと新規テストが全て通っていること。結果を成果物に記録する

### 役割の起動ルール

- タスクの大きさで起動する役割を変える(小さなバグ修正は 実装者→レビュワー→QA だけ、など)
- UIに関係しないタスクではデザイナーを呼ばない
- 全役割に「人間に聞く」出口(need_human)を持たせる。推測で進めない

### 最小構成(フェーズ1)

プランナー、実装者、レビュワー、QAの4役に、登録時のみ動くプロジェクト把握担当を加えた構成。設計者とデザイナーは一周動いてから追加する。

## 5. タスクの状態遷移

```
queued
  → planning(プランナー)
  → [人間承認: 計画]
  → designing(設計者/デザイナー。不要なら飛ばす。複数リポジトリのタスクでは設計者は必須)
  → [人間承認: デザイン仕様]  ※UIを伴うタスクのみ
  → implementing(実装者)
  → reviewing(レビュワー)
       ├ changes_requested → implementing
       └ approve → qa
  → qa(QA)
       ├ failed → implementing(必要ならデバッガー経由)
       └ passed → [人間承認: 最終確認(見た目・挙動)]
  → integrating(統合担当: ローカルブランチ+PR本文下書き)
  → done
```

- どの状態からでも `needs_input`(人間の回答待ち)、`human_working`(人が手作業中。5.2参照)、`failed`、`cancelled` に移れる
- 差し戻し(レビュー/QAの往復)は3回まで。超えたら自動で `needs_input`
- 承認ポイントは「計画」「最終確認」の2か所を基本とし、デザインにこだわるタスクでは「デザイン仕様」も加える。慣れたら省略可能にする
- `needs_input` はGUIで目立たせる(放置されやすいため)

### 5.1 プロジェクト登録フロー(最初に1回)

1. GUI/CLIで対象リポジトリのパスを登録する
2. プロジェクト把握担当が調査する(読み取りが中心。ビルドと既存テストの実行を試す)。ビルド/テスト/起動方法、構成、規約、QAの方法、テスト基盤の有無と種類を、プロジェクトプロファイルにまとめる
3. 人間がプロファイルを確認・修正して承認する
4. **テスト基盤が無い、または不十分なら、「テスト基盤整備」タスクを自動で作成する。** 通常のパイプライン(計画 → [計画承認] → 実装 → レビュー → QA)で進める。対象プロジェクトのコードを変更するため、計画承認は必須。整備が完了するまで、そのプロジェクトの通常タスクは開始しない(テスト先行の例外として人間が承認した場合を除く)
5. Flutter/iOSなど、プラットフォームごとのテスト基盤(`flutter test`、XCTestなど)も、プロファイルの「QAの方法」と合わせて記録する

### 5.2 人による手作業との並行(ハンドオフ)

同じソースコードに対して、エージェントと人が**交互に**作業する(同時には触らない)ことを前提にする。AIが途中まで進めたものに、人が手を加えるケースも含む。

- **作業場所**: 人も、**そのタスクのworktreeを開いて**編集する。GUI/CLIに「エディタで開く」を用意する。普段のフォルダには触れない。gitは同じブランチを複数のworktreeで同時にチェックアウトできないため、人が別の場所でタスクのブランチを開く方式は避ける
- **`human_working` 状態**: 「人が引き取る」操作で、そのタスクのエージェントの実行を止めてロックする。ロック中はエージェントを起動しない。「エージェントに戻す」操作でロックを解除する
- **戻すときの処理**: 未コミットの変更を検出する(人がコミットするか、ツールが人のコミットとして記録する)。コミットの作者は、エージェントと人で区別できるようにする。人の変更の差分の要約を、次の役割への入力に加える
- **承認の失効**: 人が変更した後は、それまでのレビューとQAの結果を失効させ、**レビューからやり直す**(小さな修正でも省略しない)。承認は「承認した時点のコミット」に紐づけ、新しいコミットがあれば無効とする
- **成果物の更新**: 人が方針を変えた場合は、`plan.md` や `design.md` を人が直すか、プランナー/設計者に再評価させる。ツールがそのことを促す
- **ベース更新**: 本体のコードが進んでいるとき、タスクのブランチを最新に追従させる操作を用意する。衝突したら `needs_input` にして、人が解決する。統合の前に毎回チェックする
- **実行中の警告**: エージェントが動いているworktreeには、「実行中のため触らないでください」と表示する
- **worktreeの準備**: 依存パッケージやビルド結果はworktreeごとに必要になる。準備手順はプロジェクトプロファイルに記載する

### 5.3 複数リポジトリにまたがるタスク

会社のメインサービスのように、フロントエンドとバックエンドなどが別リポジトリのケースを想定する。

- **プロジェクトは「1つ以上のリポジトリのまとまり」**とし、各リポジトリに役目(フロント、バックエンドなど)を持たせる。プロファイルは2段にする
  - リポジトリごと: ビルド、テスト、規約
  - プロジェクト全体: 全体の起動方法(両方を立ち上げる手順)、API仕様の置き場所、QAの方法
  - プロジェクト把握担当は、リポジトリごとに調べ、プロジェクト全体のプロファイルにまとめる
- **タスクが複数のworktreeを持つ。** プランナーが `plan.md` に「このタスクで変更するリポジトリ」を書き、その分だけworktreeとブランチを作る(ブランチ名は共通にする)
- **インターフェース契約。** 複数リポジトリのタスクでは設計者を必須とし、`design.md` に契約(APIのリクエスト/レスポンスの形など)を書く。これを、各リポジトリの実装者の共通の入力にする
- **実装者はリポジトリごとに別々に、順番に動かす**(バックエンド→フロントが基本)。各実装者は、自分のリポジトリのworktreeにだけ書き込める。権限が絞れて安全で、セッションの文脈も小さく済む
- **レビュー**: リポジトリごとの差分に加え、「契約と合っているか」を横断で確認する
- **QA**: プロジェクトプロファイルの「全体の起動方法」で、関係するリポジトリを一緒に立ち上げて確認する
- **統合**: リポジトリごとにローカルブランチとPR本文の下書きを作る。マージの順序と、PR同士の相互リンクをまとめて提示する。pushとPR作成は、これまで通り人が行う
- **サンドボックスの書き込み許可**は、そのタスクのworktree(複数)だけにする。**ハンドオフ**(5.2)は、そのタスクの全worktreeをまとめてロックする
- 当面は、全リポジトリを書き込み可として扱う。「参照のみ」の区分は、必要になった時点で追加する
- **フェーズ1は1リポジトリで進める**が、データの形(`projects`、`repos`、`task_repos`)は、最初から複数リポジトリを許す形にする

## 6. 成果物と判定の受け渡し

- タスクごとにディレクトリを持ち、各役割の成果物を保存する(ローカルのデータディレクトリ配下)
- 各成果物の先頭に、機械が読める形式(JSON等)で判定を残す。状態遷移はこれだけを見る
- 会話ログと成果物は全部残し、「なぜその判断をしたか」を後から追えるようにする
- **設計判断ログ(`decisions.md`)をプロジェクトごとに持つ。** 設計者・デザイナーが、重要な設計判断とその理由を追記し、次のタスクの各役割が読む。タスクごとの `design.md` が、このプロジェクトの判断の蓄積と矛盾しないようにするため。会社のリポジトリにファイルを増やさないよう、置き場所はツールのデータディレクトリ側(例: `~/.agent-team/projects/<id>/decisions.md`)とし、必要に応じてworktreeに読み取り用にコピーする
- 役割間やオーケストレーターに渡す内容は「要約+判定」だけ。詳細は成果物のパスで参照する(記憶のあふれと、コストの増加を防ぐ)

## 7. 安全方針(個人・会社共通)

会社のコードを触らせる前提で、個人利用でも同じ安全側の設定にする。

### 7.1 pushをさせない

- エージェントはローカルのworktreeとローカルブランチまで。remoteへのpush、PR作成、リモートブランチ操作は行わない
- 多層で防ぐ:
  1. Claude Codeの権限設定で `git push`、`gh pr create` などをdeny
  2. worktree/リポジトリに `pre-push` フックを入れ、実行されたら必ず失敗させる
  3. エージェント実行時の環境にGitHubの認証情報(トークン、SSH鍵)を渡さない
- pushとPR作成は人間が手元で行う。統合担当は、ブランチ名、変更履歴、PR本文の下書きを成果物として用意するところまで

### 7.2 そのほか

- 書き込み範囲はworktree内に限定。worktree外への書き込みを禁止する
- シークレット類(`.env`、鍵、認証情報ファイル)は読ませない
- 危険なコマンド(再帰的な削除、システム設定変更など)はdeny
- ネットワークは必要最小限(パッケージ取得など)。許可ドメインは設定で管理する
- 上限: タスクごとのトークン/時間、リトライ回数、同時実行数(初期は1〜2)。超えたら `needs_input`。利用枠の消費ペースを見ながら、同時実行数を調整する(3.1参照)
- 会社用の追加制限が必要になったら、プロジェクト単位の設定で強められるようにしておく(ワークスペース概念は導入しない)

### 7.3 サンドボックス

Claude Codeのサンドボックス(Bashコマンドを、OSの機能で囲いの中に閉じ込める仕組み)を採用し、7.1・7.2の仕組み(許可設定、`pre-push` フック、認証情報を渡さない)と**重ねて**使う。

- 設定の方向性(具体値はClaude Codeが最新ドキュメントを見て決める):
  - `sandbox.enabled: true`、`failIfUnavailable: true`(サンドボックスが使えなければ起動しない)
  - `allowUnsandboxedCommands: false`(囲いの外での再試行を禁止)。`--settings` で渡すと「管理者必須」扱いになり、**リポジトリ側の設定ファイルによる囲いの緩和が無視される**ため、会社のリポジトリ対策になる
  - 書き込みは作業ディレクトリ(worktree)を中心にする
  - `sandbox.credentials` で `~/.ssh`、`~/.aws` などの読み取りと、`GITHUB_TOKEN` 等の環境変数を禁止する
  - ネットワークは許可ドメインを最小にする。GitHubへの通信を許可しなければ、サンドボックス内からpushできない
- `.git` 内の `hooks` と `config` は、サンドボックス内から書き換えられない。`pre-push` フックの設置は、ツール側(サンドボックスの外)で行う
- **サンドボックスの外で動くもの**(Read/Edit/Writeツール、WebFetch、MCPサーバー、フック)は、許可設定で制御する(例: worktree外へのEditをdenyする)
- 制約: ネイティブWindowsでは使えない(Macが前提)。docker、一部のGo製CLI、SSH経由のgitなど、失敗するものがある。モバイルQA(`xcodebuild`、シミュレータ、Maestro、Flutter)は、作業ディレクトリ外への書き込みが必要で、許可の追加が要る見込み(要検証)
- `claude -p` でサンドボックスがどう効くかは未確認。フェーズ1で実際に動かして確認する

### 7.4 利用前の確認事項(会社)

- AIコーディングツールの利用可否、ソースコードを外部APIに送ってよい範囲、使うアカウント(会社契約か個人か)
- 個人で作ったツールを会社で使うことについて、就業規則(副業・知的財産)

## 8. チケット連携(Notion中心、軽く)

### 8.1 入口

- GUIにNotionのページURLを貼ると、タイトルと本文(仕様・不具合内容)を取り込み、ローカルのタスクを作成する。元ページへのリンクを保持
- ローカルのGUIから直接タスクを作る入口も用意する(外部サービスなしで動かせる)
- 自動ポーリングは行わない
- 会社のNotionのチケットは「1ページ=1チケット、本文に仕様や不具合内容」の形式。本文をそのままプランナーへの入力にし、必要な要点は `plan.md` に写して、写した版を実行時の基準にする

### 8.2 取得方法

- Notion APIの専用インテグレーション(対象DBのみ共有、読み取り専用)を第一候補にする
- 会社のNotionでインテグレーションを作れない場合に備え、**本文を貼り付けて取り込む**手段も用意しておく

### 8.3 書き戻し

- 初期は書き戻しをしない。計画の要約、PR用の文面、QAの結果は、GUIにコピーしやすい形で表示し、人間がNotionに貼る
- 将来、書き戻しが必要になったら、GUIで内容を確認してから投稿する形で追加する

### 8.4 アダプター分離

チケット元はアダプターとして分離する(Notion、ローカル入力、将来のGitHub Issues)。プロパティやステータスの対応は、プロジェクトごとの設定ファイルに持たせる。

## 9. QA

- プロジェクトプロファイルに「QAの方法」を持たせ、QAは種類別の道具を差し替える
  - Web: ブラウザ操作(ヘッドレスブラウザ、またはClaude in Chrome)
  - モバイル(iOS): iOSシミュレータをMaestro等で操作
  - Flutter: 上記に加え `flutter test` / integration_test を併用
- 成果物の形式は共通(合否、証拠、再現手順)にして、GUIは種類を意識せず表示できるようにする
- QAは受け入れ条件を1つずつ確認し、通った探索フローはYAML等で保存して次回から決まった手順で再実行する
- Flutterは、操作対象のUI部品にSemanticsラベルを付ける規約をプロジェクトプロファイルと実装者/デザイナーの役割に入れる
- シミュレータは共有資源として貸し出し管理する(1タスク1台、足りなければ待機)
- 実機が必要な確認(カメラ、センサー、プッシュ通知など)は自動QAの対象外とし、人間の確認ポイントに回す
- 見た目の良さは自動判定しきれないため、デザイナーのレビュー+人間の最終承認で担保する

## 10. デザインの進め方

- デザイナーが先に、プロジェクトごとのデザイン方針(トーン、余白、配色、コンポーネントのルール)を文書化し、実装・レビューの基準にする
- QA時のスクショをデザイナーが仕様と見比べてレビューする(`design-review.md`)
- 最終的な見た目の判断は、GUIでの人間承認で行う

## 11. 別PCでの運用(GitHubでの共有)

- このツールのリポジトリをGitHubに置き、別のPCでcloneして0から環境を作る
- リポジトリに入れるもの: サーバー、GUI、役割定義、状態遷移の定義、設定のサンプル、`doctor` コマンド
- リポジトリに入れないもの(`.gitignore`): 実行履歴のDB、ログ、成果物、PC固有の設定(対象プロジェクトのパス、トークン等)。ローカルのデータディレクトリ(例: `~/.agent-team/`)に置く
- ツール本体のリポジトリには、会社固有の情報(社名、プロジェクト名、チケット内容)を入れない
- セットアップは `git clone` → `npm install` → 起動、で動く形にする
- `doctor` コマンドで前提(Claude Code、Node、git、Xcode、Maestro、Flutter等)を検査し、足りないものを教える。使えない機能は無効化して起動できるようにする
- `doctor` は、環境変数 `ANTHROPIC_API_KEY` が設定されていたら警告する(意図しない従量課金の防止)。あわせて、現在の認証方式(サブスクかAPIか)を表示する
- 役割定義はMarkdownなので、調整した内容もGitHub経由でそのまま共有される
- 個人PCと会社PCは別々にcloneして独立して動かす。両PC間でプロジェクトやタスクの履歴は引き継がない

## 12. データモデル(概要)

- `projects`: id、名前、プロジェクト全体のプロファイル(全体の起動方法、QAの方法、API仕様の置き場所、規約)
- `repos`: id、project_id、パス、役目(フロント/バックエンド等)、リポジトリ単位のプロファイル(ビルド/テスト/規約)
- `task_repos`: task_id、repo_id、worktreeのパス、ブランチ名
- `tasks`: id、project_id、タイトル、本文、取り込み元(種別、URL)、状態、優先度、現在の作業者(エージェント/人)、作成/更新日時
- `runs`: id、task_id、役割、モデル、状態、開始/終了、判定、使用トークン/時間/コスト見積もり
- `events`: id、run_id、種別、内容、日時(会話・ツール実行ログ、GUIへの配信元)
- `artifacts`: id、task_id、run_id、種別、パス、判定
- `approvals`: id、task_id、種別(計画/デザイン/最終)、結果、コメント、日時

## 13. 開発フェーズ

1. **フェーズ0**: 本設計メモを確定し、リポジトリの `CLAUDE.md` / `docs/` に置く
   - 任意の練習: Claude Codeの標準機能(`.claude/agents/` のサブエージェントとスラッシュコマンド)で、役割プロンプトを試作して、どんな役割分担がしっくりくるかを先に確かめる。固めた役割定義は、そのまま `roles/*.md` に移せる
2. **フェーズ1**: CLIのみで一周させる(プロジェクト登録→プロファイル作成→チケット→worktree→プランナー→実装者→レビュワー→QA→ローカルブランチとPR本文下書き)。安全設定(7.1)、サンドボックス(7.3)、人への引き継ぎの最小機能(5.2。CLIで「人が引き取る/エージェントに戻す」)もここで実装
   - **フェーズ1の最後に、簡易な見える化ページを追加する。** 読み取り専用で、操作はCLIのまま。`agent-crew serve` のようなコマンドで起動し、ブラウザで開く
     - 表示: プロジェクトごとのタスク一覧と状態(`needs_input`、承認待ち、`human_working` を目立たせる)、実行中の役割、直近のイベント、成果物へのリンク(`plan.md`、`qa-report.md`、スクリーンショットなど)
     - 作り方: SQLiteを読むだけの薄いページ。自動更新は、定期的な再読み込みで十分。UIの作り込みはフェーズ2で行う
     - 安全: `127.0.0.1` のみで待ち受ける(他のPCからは見えない)。操作系の機能は持たせない
   - フェーズ1は1プロジェクト=1リポジトリで進めるが、データの形(`projects`、`repos`、`task_repos`)は、最初から複数リポジトリを許す形にする(5.3)
3. **フェーズ2**: 読み取り専用GUIの本格化(フェーズ1の簡易ページを作り込む。タスク一覧、実行状況、ログ、成果物の閲覧。デザインにこだわる)
4. **フェーズ3**: 操作できるGUI(チケット投入、承認、停止、再実行、Notion取り込み、人への引き継ぎ=「エディタで開く」「エージェントに戻す」)
5. **フェーズ4**: 設計者、デザイナーの追加。このツール自身を最初の対象プロジェクトにして、以降の開発をツール自身に行わせる
6. **フェーズ5**: 複数リポジトリ対応(5.3。フェーズ4で入る設計者の「インターフェース契約」を使う。会社のメインサービスでの利用に必要)
7. **フェーズ6**: モバイルQA(iOSシミュレータ)、Flutter対応、書き戻し等の拡張

各フェーズは縦に薄く通す(小さくても最初から最後まで動く状態にする)。
