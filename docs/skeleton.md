# 骨格(GUI・フェーズ2)

構造は `docs/structure.md`。

## ナビゲーション

- 共通ヘッダー: 左にロゴ(`/` へ)、プロジェクトのセレクト(S5 へ)。右に接続状態(● 接続中 / ○ 再接続中)と「読み取り専用」
- 詳細画面の上部にパンくず(`プロジェクト / #12 タイトル / 実行 #45`)
- 対応待ち(F1)の件数は、ブラウザのタブのタイトルにも出す(`(2) agent-crew`)。タブを開きっぱなしにする使い方のため

# 骨格(フェーズ3: 操作)

## 共通ヘッダー

```
┌ agent-crew [プロジェクト▼]   [+ チケット]      ● 自動実行中 [一時停止]  ● リアルタイム ┐
```
- 自動実行の状態: `● 自動実行中` / `‖ 一時停止中` / `CLI の run が実行中`。ボタンで切り替える
- 利用枠(フェーズ7): 自動実行の状態の左に `利用枠 32%`(窓のうち最も高い使用率。80% 以上は注意の色)。窓ごとの値とリセットの時刻はツールチップ。上限で自動の一時停止に入ったら `利用枠のため停止中(10/12 15:00 に再開)`

## S2 タスク詳細の操作欄

```
┌ 計画を確認して承認してください ─────────────────────────────────┐
│ plan.md を読む →                                                 │
│ コメント(任意)[                                              ] │
│ [承認する]  [却下して差し戻す…]                                  │
│ ▸ CLI で操作する(コマンドを表示)                                │
└─────────────────────────────────────────────────────────────────┘
```
- 却下は理由の入力欄を開いてから送る。回答も同じ形(本文必須)
- 実行中は「エージェントが実行中です」のバナーに [停止] を置く。押すと確認(「実行中の claude を止めます」)を出す
- 人が作業中は [エディタで開く] [エージェントに戻す]
- 取り消しは確認つき。破壊的な操作(停止・取り消し)のボタンは赤系、主な操作は塗りつぶし、それ以外は枠線
- 送信中はボタンを無効にし、失敗したら欄の中に理由を出す(例: 未コミットの変更があります)

# 骨格(フェーズ4: 設計の段)

## S2 タスク詳細

- パイプラインに「設計」「デザインの承認」を足す。このタスクで動かさない段は、点を破線にして文字に取り消し線を引く(飛ばす)
- 計画の承認欄に、承認したあと実装の前に動かす役割のチェックを置く。初期値はプランナーの判定で、その理由を下に添える

```
┌ 計画を確認して承認してください ─────────────────────────────────┐
│ plan.md を読む →                                                 │
│ [コメント(任意)                                              ] │
│ 承認したあと、実装の前に動かす役割                               │
│ [x] 設計者を動かす(design.md) [ ] デザイナーを動かす(ui-spec.md)│
│ プランナーの判断: モジュールの境目を決める必要があるため         │
│ [承認する]  [却下して差し戻す…]                                  │
└─────────────────────────────────────────────────────────────────┘
```

- デザイン仕様の承認待ちは、`ui-spec.md` と `design.md` へのリンクと、承認・却下(理由必須)
- 読み取り専用(`serve --no-worker`)では、ボタンの代わりに CLI のコマンドを出す

## S2 タスク詳細(4c: 実装後のデザインレビュー)

- パイプラインの QA と最終確認の間に「デザインレビュー」(デザイナーを動かさないタスクでは飛ばす)
- 「撮影した画面」の欄: 画面(パス)ごとに、幅 1280 と幅 390 の、それぞれライト・ダークの画像を並べる。画像を押すと生ファイルを開く。撮れなかったものは理由を出す。最終確認の判断材料。Flutter のアプリ(フェーズ6)は、画面の ID ごとに iOS シミュレータのライト・ダークを並べ、幅の代わりに機種(例: iPhone 17)を出す

## S2 タスク詳細(6c: 報告)

- 主欄の「撮影した画面」と「実行」の間に「報告」の欄(注記: Notion などに貼る。投稿は人が行う)
- 先頭に「すべてをコピー」と「元のページを開く」(取り込み元の URL があるときだけ)
- 節(概要・受け入れ条件・QA の結果・デザインレビュー・PR の下書き。まだ無いものは出さない)ごとに、見出しとコピーのボタン、Markdown の中身(高さを抑えてスクロール)

## S2 タスク詳細(フェーズ10: コーディネーター)

- コーディネーターで進める企画(状態「進行中(コーディネーター)」)のパイプラインは、最後に書いた段(実行の記録から)を現在地にする。まだ何も書いていなければ調査。止まったときもその段で止まって見せる
- コーディネーターの一手の記録(`coordinator-log.md`)は成果物の欄に出る

## S2 タスク詳細(フェーズ8: 分割と自動承認)

- 計画の承認の欄: プランナーが分割を提案したときだけ、「子タスク N 個に分割して進める(題1 → 題2 …)」のチェックを出す。選んで承認すると、子タスクを作り、親は「分割済み」になる
- 分割済みの親: パイプラインは計画の承認までが済み。主欄の先頭に「子タスク」の欄(順番、#番号と題、状態)。子のページのメタ情報に「分割の親: #番号 題」
- アクティビティ: 「計画の自動承認」「自動承認しない(理由)」「差し戻し(理由の要約)」の行
- 完了したタスク: 主欄の「報告」の前に「振り返りの提案」の欄(種類「規約 / 設計判断」、内容、状態「採用済み / 却下」、未決のものに「採用」「却下」のボタン。却下したものは採用し直せる)。読み取り専用では CLI のコマンドを出す

## S2 タスク詳細(フェーズ9: 企画の承認)

- 見出しは段ごとに何を承認するかを書く(「戦略(strategy.md)を確認して承認してください」「要件(scope.md)…」「開発のチケット(handoff.md)…」)
- 「まず読むもの」: 本文をボタン(「strategy.md を読む」)で目立たせ、その横に中身の説明。下に補助の資料(スライド、批評担当の点検結果。引き渡しではワイヤーフレームと構造も)を説明つきで並べる
- 「決めてほしいこと」: 問いを1件ずつ番号つきで、誰からか(企画担当、批評担当など)を添える。下に批評の must と should の件数

```
┌ 戦略(strategy.md)を確認して承認してください ─────────────────┐
│ まず読むもの                                                     │
│ [strategy.md を読む]  戦略の本文(誰の・何の課題を…)             │
│ strategy.slides.md  同じ内容のスライド(Marp)                    │
│ critique-strategy.md  批評担当の点検結果                         │
│ 決めてほしいこと(承認のコメントで答えるか、却下して書き直させる) │
│ 1. 動かす先を Web にするか — 企画担当                            │
│ 2. 成功指標の目標値 — 批評担当                                   │
│ 批評の should 7 件(参考)                                       │
└──────────────────────────────────────────────────┘
```

## S2 タスク詳細(フェーズ9: 引き渡し先)

- 引き渡しの承認欄の「開発のタスクを作るプロジェクト」: 既存のプロジェクト(リポジトリのあるもの)、「<企画のプロジェクト> にリポジトリを登録する」(リポジトリが無いときだけ。既定)、「新しいプロジェクトを作る」
- 後の2つを選ぶと、リポジトリのフォルダの入力欄(新しいプロジェクトでは名前も)と説明「手元のリポジトリか、空のフォルダ(無ければ作って git init します)。GitHub などにリポジトリがあるなら、先に clone したフォルダを指定」

```
開発のタスクを作るプロジェクト [kakeibo にリポジトリを登録する ▾]
リポジトリのフォルダ [/Users/me/dev/kakeibo-app          ]
手元のリポジトリか、空のフォルダ(無ければ作って git init します)。登録後、プロファイルを承認すると開発が始まります
```

## S5 プロジェクト(フェーズ9)

- プロジェクト画面のリポジトリの欄は「パス」と「ベースのブランチ」(タスクのブランチの元で PR の向け先)を説明つきで出す。リポジトリが2つ以上のときだけ「名前」(プロジェクトの中でリポジトリを区別する名前。--role)も出す。リポジトリの無いプロジェクトでは登録のコマンドを出す
- タイトルの行の右に「+ チケット」(リポジトリがあるとき)と「+ 企画」のボタン
- プロファイルが承認待ちなら、注意の欄に「プロファイルを承認する」のボタン(テスト基盤が無ければ「整備を待たずに開発を始める」のチェック)。作っている間は「プロジェクト把握担当がプロファイルを作っています」、失敗したら理由と「作り直す」

```
shop                                   [+ チケット] [+ 企画]
```

## S5 プロジェクト(v0.23: 設定)

- 右の欄の先頭に「設定」。「最終確認の後の取り込み方」を2択(「PR を作る」/「<ベースのブランチ> に取り込む」。それぞれ説明つき)、その下に「計画の自動承認」「振り返り」「企画をコーディネーターで進める」のチェック(それぞれ1行の説明)。選んだらすぐ保存し、画面を読み直す(リポジトリの欄の「ベースのブランチ」の説明が、取り込み方に合わせて変わる)
- 読み取り専用(serve --no-worker)では選べないようにし、切り替えの CLI のコマンドを並べる

```
設定
最終確認の後の取り込み方
(•) PR を作る          タスクごとにブランチと PR の下書きを残す…
( ) main に取り込む     ツールがローカルの main に fast-forward で…
─────────────
[ ] 計画の自動承認
[x] 振り返り
[ ] 企画をコーディネーターで進める
```

## S1 ダッシュボード(フェーズ9)

- 「プロジェクト」の欄: 行ごとに名前(プロジェクト画面へ)、種類(開発 / 企画用)、プロファイルの状態(未承認なら注意の色)、進行中のタスク数。見出しの右に「+ プロジェクト」

## S2 タスク詳細(デザインレビューで止まったとき)

- 人の判断待ちの欄で、デザインレビューで止まったとき(撮影できないなど)は、「回答して再開する」の横に「デザインレビューを飛ばして最終確認へ」と「実装者に差し戻す…」(理由が必須)を出す

## S2 タスク詳細(最終確認)

- 見出しは「実装の結果を確かめて最終承認してください(承認すると PR の下書きを作ります)」
- 「まず読むもの」: `qa-report.md`(受け入れ条件ごとの結果)をボタンで目立たせる
- 「続けて確かめるもの」: 番号つきで、`diff.patch`(意図しない変更が無いか)、`test-changes.md`(テストを弱めていないか)、`review.md`(残った should・nit を受け入れてよいか)、`design-review.md`(あれば。撮影した画面の枚数も)、`impl-notes.md`(計画から変えたこと)
- 最後に「手元で見るならエディタで開く(見るだけ)。直してほしい点は却下で差し戻す。承認すると pr-draft.md を作る。push と PR は人」。操作は承認・却下と「エディタで開く(見るだけ)」

## S2 タスク詳細(main の最新を取り込む)

- 人の判断待ちの欄の操作名は「<既定ブランチ> の最新を取り込む」(worktree があるときだけ)。押すと確認のダイアログで、何が起きるかを書く
  - コミットがまだ無い: 「最新の main から作り直します(失うものはありません)。状態は変わりません」
  - コミットがある: 「最新の main をマージします。実装の後ならレビューからやり直します。衝突したら人の作業になります」
- 確認を出す操作でも、赤(危険の色)は「停止」と「取り消す」だけ

# 骨格(見直し 2026-10-17: 経緯と実行中)

運用で「実行」「アクティビティ」「実況」をほとんど見なかったため(`docs/strategy.md` の「運用で分かったこと」)。この節が、上の S1 の「実況」と S2 の「実行」「アクティビティ」の記述より優先する。

## 経緯に出す出来事

- 出す: 差し戻し(理由の要約)、レビューの指摘(must / should / nit の件数)、Must 指摘の監査、計画の自動承認・自動承認しない(理由)、人の回答待ち(理由)、タスクの失敗、警告、重なりの待ち、人の引き取り・戻し、統合、設計判断、振り返りの提案の採用・却下、利用枠の待ち・一時停止・再開、完了・取り消し(状態の変化のうち、この2つだけ)
- 出さない: そのほかの状態の変化(パイプラインと重なる)、実行の中の細かい動き(発言・ツール。実行ログで見る)、片付け、撮影の記録、コマンドの記録、実装のコミット、計画の中身、役割の失敗(実行の行に出る)
- 判定は `gui/src/lib/events.ts` の `isMilestone` に置き、S1 と S2 で共有する

## S1 ダッシュボード

- 右の欄の名前を「実況」から「実行中」に変える。対応待ちと同じ重さで左右に並べるのは変えない

```
┌ 実行中 (1) ─────────────────────────────────────┐
│ ● implementer sonnet  #13 検索を追加     3分12秒 │
│   ▸ Bash  npm test                    12秒前     │ ← 今の動き1行と、最後に動いてからの時間
│ (実行中が無ければ「実行中の役割はありません」)     │
│ 最近の出来事                                     │
│ 10:31 #12 ↩ 差し戻し  must 2件: 境界値のテスト…  │ ← 押すとタスク詳細へ
│ 10:22 #12 ✓ 計画の自動承認                       │
│ …(経緯の出来事だけ。最新 10 件)                 │
└──────────────────────────────────────────────────┘
```

- 実行中の行を押すと実行ログ(S4)へ。最後に動いてから 3 分を超えたら、その時間を注意の色にする(詰まっていないかの目安。止めはしない)

## S2 タスク詳細

- 主欄の「実行」と「アクティビティ」をやめ、主欄の最後に「経緯」を置く。既定は畳み、見出しに「差し戻し N 回・実行 M 回」を添える

```
▸ 経緯(差し戻し 1 回・実行 5 回)
  10:20 ⚙ planner sonnet   ready              $0.09  1分40秒 →   ← 実行の行。押すと実行ログへ
  10:22 ✓ 人  計画を承認 「エラー時の表示も」                    ← 承認・却下とコメント
  10:31 ⚙ reviewer opus   changes_requested  $0.21  3分02秒 →
  10:31 🔎 レビューの指摘  must 2 / should 1 / nit 0
  10:31 ↩ 差し戻し  境界値のテストがない…
  (古い順。実行中の実行は「実行中」と経過時間)
```

- 実行の行は、役割・モデル・判定(無ければ実行の状態)・費用・時間。承認は承認・合格の記録から(失効したものは薄く)。出来事は上の「経緯に出す出来事」だけ
- 実行中の役割は、これまでどおりバナーから実行ログへ辿れる
