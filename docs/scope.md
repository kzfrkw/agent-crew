# 要件(GUI・フェーズ2)

戦略は `docs/strategy.md`。フェーズ2は読み取り専用GUIの本格化(設計メモ13章)。

## 機能一覧

| # | 機能 | 内容 |
|---|------|------|
| F1 | 対応待ちの一覧 | `needs_input` / 承認待ち / `failed` / `human_working` のタスクを最上部にまとめる。理由(回答待ちの質問、失敗の理由)と、次に打つ CLI コマンドを添える |
| F2 | 実況 | 実行中の役割(タスク、役割、モデル、経過時間)と、全タスクの最新イベント(発言、ツール実行、状態変化)が流れる |
| F3 | タスク一覧 | プロジェクトごとのタスクと状態、実行中の役割、差し戻し回数、費用の合計(費用が記録された実行の合計。無ければ `-`)、更新日時。完了・取り消しは既定で畳む。絞り込み(すべて / 進行中 / 対応待ち)のボタンに、押したときに出るタスクの件数(全プロジェクトの合計)を添える。件数は「完了・取り消しも表示」に連動する |
| F4 | タスク詳細 | 状態、パイプライン上の位置、チケット本文、worktree とブランチ、承認(有効/失効)、成果物、実行の履歴、費用と所要時間の合計 |
| F5 | 成果物ビューア | Markdown を整形して表示(先頭の判定 frontmatter はバッジで表示)。画像、テキスト、差分もそのまま表示 |
| F6 | 実行ログ | 1回の実行のイベント(発言、ツール実行と結果、警告)を時系列で表示。実行中は追記されていく。生ログ(`stream.jsonl`)へのリンク |
| F7 | プロジェクト | プロファイル(承認状態、テスト基盤)、リポジトリ、設計判断ログ(`decisions.md`)、プロジェクト把握担当の実行 |
| F8 | 即時反映 | SSE で変化を受け取り、開いている画面を更新する。接続状態を表示し、切れたら自動で再接続する |
| F9 | CLI コマンドのコピー | 承認・回答・引き継ぎなど、その状態で必要なコマンドをワンクリックでコピー |

## ユーザーストーリー

- 開発者として、ブラウザを開いたら、自分の対応が必要なタスクが最上部に見えてほしい。放置を防ぐため
- 開発者として、計画の承認待ちのタスクから plan.md をすぐ読みたい。承認の判断をするため
- 開発者として、回答待ちのタスクの質問と、回答するコマンドを見たい。すぐ答えるため
- 開発者として、実行中のエージェントの発言とツール実行を、再読み込みせずに眺めたい。詰まっていないか確かめるため
- 開発者として、レビューで差し戻された理由と、その後の修正を時系列で追いたい。判定の妥当性を確かめるため
- 開発者として、タスクごとの費用と時間を知りたい。利用枠の消費を把握するため
- 開発者として、プロジェクトのプロファイルと設計判断ログを読みたい。エージェントが前提にしている情報を確かめるため

## スコープ外(フェーズ2ではやらない)

- 操作(チケット投入、承認、回答、停止、再実行、引き継ぎ、エディタで開く)→ フェーズ3
- Notion 取り込み → フェーズ3
- 認証、複数ユーザー、他のPCからのアクセス(`127.0.0.1` のみ)
- デスクトップ通知(ブラウザ通知)→ フェーズ3で操作と合わせて検討
- 費用のグラフや期間集計(合計値の表示まで)
- 検索・全文検索
- モバイル表示の作り込み(崩れない程度に対応)

# 要件(GUI・フェーズ3: 操作できるGUI)

フェーズ2の読み取り専用GUIに、操作を足す。決めたこと(2026-10-09): オーケストレーターは serve に常駐させる/チケット投入はフォームと貼り付けまで/停止は実行中の claude を止める。

## 機能一覧

| # | 機能 | 内容 |
|---|------|------|
| G1 | 常駐ワーカー | serve の中でオーケストレーターが待機し、進められるタスクがあれば自動で進める。承認・回答などの操作の直後にすぐ動く。CLI の `agent-crew run` とはロックで排他する |
| G2 | 自動実行の一時停止 | ヘッダーのスイッチで、新しい役割を起動しないようにする(実行中の役割は止めない)。一時停止中はロックを外し、CLI の run を使える |
| G3 | 承認・却下 | 計画・最終確認の承認(コメント任意)と却下(理由必須) |
| G4 | 回答 | 回答待ちに回答して再開する |
| G5 | 停止 | 実行中の claude を止め、その実行を「中止」、タスクを人の判断待ち(needs_input)にする。再開は回答か引き取り |
| G6 | 引き取り・戻す | 人が引き取る/エージェントに戻す(未コミットの変更があれば拒否されることを表示) |
| G7 | エディタで開く | タスクの worktree をエディタで開く(既定は `code`。`config.json` の `editor` で変える) |
| G8 | ベースの取り込み | タスクのブランチにベースを取り込む(衝突したら人の判断待ち) |
| G9 | 取り消し | タスクを取り消す(確認つき) |
| G10 | チケット投入 | タイトルと本文のフォーム。Notion などから本文を貼り付け、取り込み元の URL を添えられる |
| G12 | 分割(フェーズ8) | 計画の承認で、プランナーが提案した子タスクに分割して進める。分割済みの親から子タスクへ、子から親へ移れる |
| G11 | 報告(フェーズ6c) | タスク詳細に、Notion などに貼る報告(概要・受け入れ条件・QA の結果・デザインレビュー・PR の下書き)を Markdown で出す。節ごと・すべてをコピーでき、元のページを開ける。投稿は人が行う(API は使わない) |

## ユーザーストーリー

- 開発者として、計画を読んだその画面で承認したい。CLI に切り替える手間を省くため
- 開発者として、承認したらそのままエージェントが進んでほしい。`run` を打ち忘れて止まらないように
- 開発者として、おかしな方向に進んでいる実行をすぐ止めたい。利用枠の無駄を防ぐため
- 開発者として、思いついたチケットをブラウザからすぐ投入したい
- 開発者として、終わったタスクの結果をチケット(Notion)にすぐ書き戻したい。成果物を読み直してまとめる手間を省くため

## スコープ外(フェーズ3ではやらない)

- Notion API での取り込み(会社で使えるかが分かってから)
- プロジェクトの登録・プロファイルの承認の GUI(登録は年に数回なので CLI のまま)
- 再実行(失敗したタスクの retry)の GUI。失敗は引き取って直すか取り消す
- 認証(127.0.0.1 のみで待ち受けるため)。外部のサイトからの操作は、専用ヘッダーと Origin の検査で防ぐ
